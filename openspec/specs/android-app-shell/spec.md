# android-app-shell Specification

## Purpose

Определить проверяемое поведение единственного Android-приложения DeviceBridge: базовую навигацию, безопасное состояние передачи и управление встроенным локальным сервером.

## Requirements

### Requirement: Запуск в безопасном начальном состоянии

Android-приложение MUST открывать главный экран в состоянии «Сервер остановлен», пока локальный сервер не запущен пользователем.

#### Scenario: Первый запуск приложения

- **WHEN** пользователь запускает приложение до появления или запуска локального сервера
- **THEN** система показывает главный экран и статус «Сервер остановлен»
- **AND** система не показывает фиктивный адрес, код подключения или подключённый браузер

### Requirement: Верхнеуровневая навигация

Android-приложение MUST предоставлять переходы между разделами «Главная», «История» и «Настройки» и выделять текущий раздел.

#### Scenario: Переход в историю

- **WHEN** пользователь выбирает раздел «История»
- **THEN** система показывает экран истории
- **AND** элемент «История» отображается как выбранный

#### Scenario: Возврат на главный экран

- **WHEN** пользователь с другого верхнеуровневого раздела выбирает «Главная»
- **THEN** система показывает главный экран без создания дублирующихся копий раздела в back stack

### Requirement: Главный экран управляет production server

Главный экран Android-приложения MUST позволять явно запускать и останавливать production server и MUST показывать его фактическое состояние. Адрес, порт и uptime MUST отображаться только для реально работающего server instance.

#### Scenario: Сервер остановлен

- **WHEN** пользователь открывает главный экран без работающего server service
- **THEN** экран показывает состояние «Сервер остановлен» и доступное действие запуска
- **AND** не показывает устаревший или фиктивный endpoint

#### Scenario: Сервер запускается или останавливается

- **WHEN** выполняется переходное lifecycle-действие
- **THEN** экран показывает соответствующее состояние
- **AND** блокирует повторную конфликтующую команду

#### Scenario: Сервер запущен

- **WHEN** production server успешно занял LAN endpoint
- **THEN** экран показывает browser URL, действие копирования, uptime и действие остановки
- **AND** доступное название действия копирования сообщает, что копируется адрес DeviceBridge

#### Scenario: Запуск завершился ошибкой

- **WHEN** server lifecycle возвращает recoverable error
- **THEN** экран показывает понятное пользовательское сообщение и действие повтора
- **AND** технические подробности не подменяют основное объяснение

### Requirement: Главный экран показывает browser pairing

Во время Running Android-приложение MUST показывать действующий одноразовый код с оставшимся временем, pending pairing requests и фактические активные browser sessions. Код и session-сведения MUST исчезать при завершении server lifecycle.

#### Scenario: Сервер ожидает подключение браузера

- **WHEN** production server работает и активных browser sessions нет
- **THEN** главный экран показывает шестизначный pairing code, срок его действия и краткую инструкцию для компьютера
- **AND** не показывает фиктивный подключённый browser client

#### Scenario: На телефоне ожидается решение

- **WHEN** browser client правильно ввёл код и создал pending request
- **THEN** Android UI показывает browser label, source IPv4 и действия «Разрешить» и «Отклонить»
- **AND** доступное название каждого действия однозначно относится к этому запросу

#### Scenario: Browser session активна

- **WHEN** пользователь разрешил подключение
- **THEN** главный экран показывает browser client в списке подключённых и предоставляет действие отключения
- **AND** число браузеров совпадает с фактическим session state

#### Scenario: Сервер остановлен

- **WHEN** server lifecycle покидает Running
- **THEN** главный экран не показывает прежний pairing code, countdown, pending requests или active sessions

### Requirement: Недоступность передачи без активной сессии

Android-приложение MUST блокировать transfer actions без работающего сервера и активной browser session. После подключения действия «Текст» и «Файлы» MUST быть доступны в рамках реализованных capabilities.

#### Scenario: Действия при остановленном сервере

- **WHEN** пользователь находится на главном экране в состоянии «Сервер остановлен»
- **THEN** действия «Текст» и «Файлы» отображаются недоступными
- **AND** интерфейс сообщает, что сначала потребуется запустить сервер и подключить браузер

#### Scenario: Сервер запущен без авторизованного браузера

- **WHEN** production server работает, но ни один browser client не авторизован
- **THEN** действия «Текст» и «Файлы» остаются недоступными
- **AND** интерфейс предлагает завершить pairing с браузером

#### Scenario: Browser авторизован до реализации transfer

- **WHEN** хотя бы одна browser session активна
- **THEN** действия «Текст» и «Файлы» доступны и открывают соответствующий flow
- **AND** каждый flow требует явного recipient и подтверждения пользовательской операции

### Requirement: Android shell предоставляет file flow для выбранной session

Android-приложение MUST позволять выбрать один или несколько файлов, показать recipient и metadata, подтвердить отправку и наблюдать очередь текущего server generation.

#### Scenario: Активна одна browser session

- **WHEN** пользователь открывает действие «Файлы» и выбирает документы
- **THEN** Android показывает выбранную session, имена и размеры файлов
- **AND** не начинает передачу до явного подтверждения

#### Scenario: Активно несколько browser sessions

- **WHEN** пользователь готовит Android → Browser transfer
- **THEN** Android требует явно выбрать одну session
- **AND** не выполняет скрытую рассылку всем browsers

#### Scenario: Отображаются active transfers

- **WHEN** queue содержит queued, active или terminal items текущего generation
- **THEN** Android показывает отдельные карточки с направлением, progress и доступным действием отмены или повтора
- **AND** карточки не подменяют состояние text flow

### Requirement: Android принимает системный share только в preview

DeviceBridge MUST принимать один или несколько content URI через ACTION_SEND и ACTION_SEND_MULTIPLE, но MUST NOT начинать передачу до проверки metadata, выбора активной session и подтверждения пользователя.

#### Scenario: Другой Android app делится одним файлом

- **WHEN** DeviceBridge получает ACTION_SEND с доступным content URI
- **THEN** приложение открывает file preview
- **AND** требует выбрать recipient и подтвердить отправку

#### Scenario: Другой Android app делится несколькими файлами

- **WHEN** DeviceBridge получает ACTION_SEND_MULTIPLE с доступными content URI
- **THEN** приложение показывает каждый допустимый item
- **AND** недоступный URI отмечается ошибкой без crash всего preview

### Requirement: Android управляет destination через системный picker

Для Browser → Android transfer приложение MUST запросить у пользователя destination через Storage Access Framework и MUST предоставлять явное действие открытия успешно сохранённого файла. Широкое storage permission MUST NOT требоваться.

#### Scenario: Получено file offer

- **WHEN** browser предлагает допустимые файлы
- **THEN** Android показывает sender, имена, размеры и действие выбора папки
- **AND** transfer не принимается скрыто в неизвестное location

#### Scenario: Файл успешно сохранён

- **WHEN** transfer завершён и checksum совпал
- **THEN** Android показывает completed и действие открытия файла
- **AND** передаёт внешнему viewer только scoped content URI permission

### Requirement: Пустая история

Android-приложение MUST показывать понятное пустое состояние, если сохранённых передач ещё нет.

#### Scenario: История без операций

- **WHEN** пользователь открывает историю до первой передачи
- **THEN** система сообщает, что история пока пуста
- **AND** интерфейс не показывает тестовые или вымышленные операции

### Requirement: Системная тема и доступность

Android-приложение MUST корректно отображать базовые экраны в светлой и тёмной системной теме, а интерактивные элементы MUST иметь доступные текстовые названия.

#### Scenario: Переключение системной темы

- **WHEN** системная тема устройства меняется между светлой и тёмной
- **THEN** базовые экраны используют соответствующую цветовую схему без потери читаемости

#### Scenario: Чтение навигации экранным диктором

- **WHEN** служба доступности фокусируется на элементе верхнеуровневой навигации
- **THEN** система предоставляет понятное название раздела и состояние его выбора

### Requirement: Android shell предоставляет text flow для активной session

Android-приложение MUST открывать text flow с главного экрана, показывать выбранную активную browser session и возвращаться к безопасному состоянию, если получатель отключился до подтверждения.

#### Scenario: Подключён один браузер

- **WHEN** пользователь выбирает действие «Текст» при одной активной browser session
- **THEN** Android открывает text flow с этой session как получателем
- **AND** до подтверждения позволяет проверить содержимое и распознанный тип

#### Scenario: Подключено несколько браузеров

- **WHEN** пользователь открывает text flow при нескольких активных sessions
- **THEN** Android требует явно выбрать одного получателя
- **AND** не выбирает скрытую рассылку всем clients

#### Scenario: Получатель отключился

- **WHEN** выбранная session отозвана или потеряна до отправки
- **THEN** действие отправки блокируется
- **AND** Android предлагает выбрать доступную session или повторить pairing

### Requirement: Android показывает безопасную и понятную browser label

Pending request и список активных sessions MUST показывать нормализованную информационную browser label. Распознанный Яндекс Браузер MUST отображаться как «Яндекс Браузер», а неизвестный client MUST получать нейтральную метку без ложного указания Chrome или другого продукта.

#### Scenario: Подключается Яндекс Браузер

- **WHEN** pending request содержит нормализованную метку распознанного Яндекс Браузера
- **THEN** Android показывает «Яндекс Браузер» в запросе подтверждения и активной session
- **AND** не подписывает client как Chrome или Google Chrome

#### Scenario: Browser family не определена

- **WHEN** session metadata не позволяет надёжно определить browser family
- **THEN** Android показывает нейтральное название «Браузер» с допустимой платформой при её наличии
- **AND** не показывает сырой User-Agent или непроверенную разметку
