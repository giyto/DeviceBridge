# server-lifecycle Specification

## Purpose

Определить пользовательский production lifecycle локального сервера DeviceBridge: явный запуск, foreground-работу, доступный LAN endpoint, обработку разрешений и сети, восстановление состояния интерфейса и гарантированное освобождение ресурсов.

## Requirements

### Requirement: Сервер работает только в явно запущенной пользовательской сессии

DeviceBridge MUST запускать production server только после явного действия пользователя и MUST NOT автоматически запускать его после загрузки телефона, запуска приложения, появления сети или восстановления процесса.

#### Scenario: Пользователь запускает сервер

- **WHEN** пользователь на видимом экране DeviceBridge выбирает «Запустить DeviceBridge»
- **THEN** система проверяет необходимые условия и запускает server lifecycle
- **AND** состояние проходит через «Запускается» к «Сервер запущен» либо к понятной ошибке

#### Scenario: Повторная команда запуска

- **WHEN** команда запуска повторяется во время запуска или работы сервера
- **THEN** система сохраняет единственный server instance и единственный listening socket
- **AND** не создаёт дублирующее уведомление

#### Scenario: Сеть появилась без действия пользователя

- **WHEN** сервер остановлен и на телефоне появляется подходящая локальная сеть
- **THEN** система может обновить доступность запуска
- **AND** сервер остаётся остановленным до явной команды пользователя

#### Scenario: Телефон перезагружен

- **WHEN** телефон завершает загрузку системы
- **THEN** DeviceBridge не запускает server service автоматически

### Requirement: Работающий сервер принадлежит foreground service

Во время работы production server система MUST поддерживать его foreground service типа `connectedDevice`. Server lifecycle MUST продолжаться при уходе Activity в фон и MUST завершаться вместе с service.

#### Scenario: Activity уходит в фон

- **WHEN** сервер работает и пользователь сворачивает приложение или закрывает Activity
- **THEN** foreground service и доступный browser endpoint продолжают работать
- **AND** постоянное системное уведомление отражает активную работу DeviceBridge

#### Scenario: Пользователь возвращается в приложение

- **WHEN** Activity создаётся заново при работающем service
- **THEN** главный экран показывает фактическое состояние того же server instance
- **AND** не запускает второй instance

#### Scenario: Процесс остановлен системой или пользователем

- **WHEN** Android полностью прекращает процесс DeviceBridge
- **THEN** listening socket и текущая серверная сессия прекращаются
- **AND** при следующем обычном запуске приложение показывает сервер остановленным без скрытого восстановления

### Requirement: Уведомление обеспечивает видимость и остановку сервера

При работающем сервере DeviceBridge MUST показывать постоянное foreground-уведомление с состоянием, локальным endpoint, фактическим числом подключённых браузеров и состоянием активной передачи. Уведомление MUST содержать действие «Остановить».

#### Scenario: Сервер успешно запущен

- **WHEN** server lifecycle переходит в состояние «Сервер запущен»
- **THEN** уведомление показывает доступный локальный адрес
- **AND** до реализации pairing показывает ноль подключённых браузеров и отсутствие активной передачи

#### Scenario: Остановка из уведомления

- **WHEN** пользователь нажимает «Остановить» в уведомлении
- **THEN** система останавливает сервер и закрывает соединения
- **AND** удаляет foreground-уведомление

#### Scenario: Разрешение уведомлений отклонено

- **WHEN** Android поддерживает runtime-разрешение уведомлений и пользователь его отклоняет
- **THEN** система объясняет, что уведомление может отсутствовать в notification drawer
- **AND** разрешает явно запустить foreground service, если Android допускает это
- **AND** сохраняет доступное действие остановки на главном экране

### Requirement: Локальные разрешения запрашиваются в момент запуска

DeviceBridge MUST объявлять необходимые сетевые и foreground-service permissions и MUST запрашивать runtime-доступ к локальной сети до открытия LAN socket на Android 17.1/API 37.1. Отказ или последующий отзыв MUST обрабатываться без crash и без открытого порта.

#### Scenario: Первый запуск сервера на API 37.1

- **WHEN** пользователь запускает сервер без выданного `ACCESS_LOCAL_NETWORK`
- **THEN** приложение показывает системный запрос разрешения в контексте действия пользователя
- **AND** открывает LAN socket только после положительного результата

#### Scenario: Пользователь отклоняет локальное разрешение

- **WHEN** пользователь отклоняет запрос `ACCESS_LOCAL_NETWORK`
- **THEN** сервер остаётся остановленным
- **AND** UI показывает понятное объяснение и способ повторить действие

#### Scenario: Локальное разрешение отозвано во время работы

- **WHEN** `ACCESS_LOCAL_NETWORK` отозвано при работающем сервере
- **THEN** DeviceBridge закрывает listener и соединения
- **AND** показывает контролируемую ошибку, требующую повторного разрешения и явного запуска

#### Scenario: Запуск на API 29

- **WHEN** пользователь запускает DeviceBridge на Android 10/API 29
- **THEN** приложение не запрашивает несуществующее runtime-разрешение локальной сети
- **AND** использует объявленное сетевое разрешение платформы

### Requirement: Пользователь получает достижимый локальный endpoint

После успешного запуска DeviceBridge MUST показывать browser URL с достижимым non-loopback IPv4-адресом подходящей локальной сети и фактически занятым свободным портом. Пользовательский URL MUST NOT содержать `0.0.0.0` или loopback-адрес.

#### Scenario: Телефон подключён к Wi-Fi

- **WHEN** на телефоне доступен подходящий IPv4-адрес Wi-Fi LAN
- **THEN** сервер принимает локальные соединения на свободном порту
- **AND** UI и уведомление показывают копируемый URL с этим адресом и портом

#### Scenario: Компьютер подключён к точке доступа телефона

- **WHEN** телефон предоставляет локальный IPv4 endpoint для своей точки доступа
- **THEN** DeviceBridge показывает адрес, достижимый клиентом этой точки доступа
- **AND** browser web shell открывается по показанному URL без интернета

#### Scenario: Подходящий адрес отсутствует

- **WHEN** система не может определить достижимый локальный IPv4 endpoint
- **THEN** сервер не начинает слушать произвольный интерфейс
- **AND** UI предлагает подключиться к Wi-Fi или включить точку доступа и повторить запуск

#### Scenario: Предпочтительный порт занят

- **WHEN** выбранный порт уже используется
- **THEN** DeviceBridge выбирает другой свободный порт либо показывает recoverable error
- **AND** никогда не показывает URL порта, который сервер фактически не занял

### Requirement: Смена сети завершает старый endpoint

DeviceBridge MUST наблюдать за состоянием и адресами локальной сети только во время server lifecycle. Потеря сети, потеря выбранного адреса или переход на другой endpoint MUST закрывать старый listener и MUST NOT автоматически переносить текущую сессию на новую сеть.

#### Scenario: Локальная сеть потеряна

- **WHEN** работающий сервер теряет сеть, на которой опубликован его endpoint
- **THEN** server lifecycle освобождает listener и переходит в recoverable error
- **AND** UI сообщает о потере локальной сети

#### Scenario: IP-адрес изменился

- **WHEN** выбранный локальный IPv4-адрес изменяется во время работы
- **THEN** старый URL перестаёт считаться действующим
- **AND** сервер останавливается и предлагает явный повторный запуск

#### Scenario: Пользователь запускает сервер после смены сети

- **WHEN** подходящая сеть снова доступна и пользователь повторяет запуск
- **THEN** DeviceBridge создаёт новый listener
- **AND** показывает новый фактический URL

### Requirement: Состояние lifecycle едино для service и интерфейса

Android UI, foreground-уведомление и server runtime MUST отражать одну фактическую state machine со состояниями «Остановлен», «Запускается», «Запущен», «Останавливается» и «Ошибка». Сохранённые UI-данные MUST NOT выдавать остановленный socket за работающий.

#### Scenario: Activity пересоздана

- **WHEN** Activity пересоздаётся из-за configuration change или возврата пользователя
- **THEN** экран подписывается на текущее process-wide состояние service
- **AND** показывает актуальные endpoint и время работы без отдельного запуска

#### Scenario: Отображается время работы

- **WHEN** сервер находится в состоянии «Запущен»
- **THEN** UI вычисляет uptime от монотонной отметки фактического старта
- **AND** пересоздание Activity не обнуляет uptime

#### Scenario: Получено устаревшее сохранённое состояние

- **WHEN** новый процесс не имеет работающего service, но UI восстанавливает ранее сохранённые данные экрана
- **THEN** фактическое состояние service имеет приоритет
- **AND** адрес и uptime не показываются как активные

### Requirement: Остановка освобождает ресурсы и допускает повторный запуск

Любая штатная остановка или recoverable ошибка MUST закрывать listening socket и клиентские соединения, отменять принадлежащие lifecycle coroutine jobs, прекращать наблюдение за сетью и удалять foreground notification. После завершения остановки новый явный запуск MUST быть возможен без перезапуска приложения.

#### Scenario: Остановка с главного экрана

- **WHEN** пользователь нажимает «Остановить DeviceBridge»
- **THEN** система переходит через «Останавливается» в «Сервер остановлен»
- **AND** освобождает все ресурсы текущего lifecycle

#### Scenario: Повторяемые циклы

- **WHEN** тест выполняет 20 последовательных циклов start → web-manifest check → stop
- **THEN** каждый запуск создаёт один доступный endpoint
- **AND** после каждой остановки порт освобождён и следующий цикл успешен

#### Scenario: Ошибка запуска

- **WHEN** service или server runtime не может завершить запуск
- **THEN** система очищает частично созданные ресурсы и показывает безопасную recoverable error
- **AND** повторный явный запуск возможен после устранения причины

### Requirement: Production server не раскрывает debug diagnostics и будущие API

Production lifecycle MUST раздавать текущие встроенные web assets без внешнего backend, но MUST NOT публиковать `/diagnostics/*`, диагностический bearer token, pairing, session token, transfer routes или другие незавершённые `/api/v1/*`.

#### Scenario: Browser открывает production endpoint

- **WHEN** пользователь открывает показанный LAN URL работающего production server
- **THEN** корневая страница, связанные assets и `/web-manifest.json` доступны по текущему контракту
- **AND** страница не выполняет внешних запросов

#### Scenario: Запрошен диагностический маршрут

- **WHEN** клиент release-сборки запрашивает `/diagnostics/health` или другой `/diagnostics/*`
- **THEN** сервер возвращает 404
- **AND** ответ не раскрывает диагностические сведения или token

#### Scenario: Запрошен будущий production API

- **WHEN** клиент без реализованного pairing запрашивает `/api/v1/status` или другой незавершённый `/api/v1/*`
- **THEN** сервер не предоставляет данные или пользовательские операции
