## Context

**Android сейчас:**
- Есть одно уведомление - постоянное «Сервер запущен» (`AndroidServerNotificationController`, канал `devicebridge_server`, `IMPORTANCE_LOW`). У него нет `setContentIntent`, есть только действие «Остановить».
- Разрешение `POST_NOTIFICATIONS` уже запрашивается при запуске сервера (API 33+). Отказ не блокирует запуск.
- Общей шины доменных событий нет. Источники состояния - три `StateFlow`:
  - `BrowserSessionRepository.state`: `pendingRequests: List<PendingBrowserRequest>`, срок ожидания 60 с;
  - `FileTransferRepository.state`: `FileTransferSnapshot`, фазы `QUEUED..FAILED`;
  - `TextTransferRepository.state`.
- Входящий файл не имеет отдельного состояния «предложение». Это элемент `BROWSER_TO_ANDROID` в фазе `CONNECTING`; остальные файлы пачки ждут в `QUEUED` и продвигаются по одному. `batchId` в состоянии не хранится.
- Принять файл без интерфейса уже умеет `TrustedAutoAcceptController`: открывает папку по умолчанию (`destinationTree`), регистрирует lease и вызывает `approve`. Отклонение - это `cancel`.
- Входящий текст сразу приходит в состоянии `DELIVERED`. Телефон сам никогда не пишет его в буфер обмена.
- Приложение не отслеживает, видно ли оно на экране: нет `ProcessLifecycleOwner` и нет зависимости `lifecycle-process`.
- `MainActivity` в режиме `singleTop` уже принимает extra от плитки (`EXTRA_START_SERVER_FROM_TILE`). В манифесте нет ни одного `BroadcastReceiver`.
- Экраны «Текст» и «Файлы» - не вкладки нижней навигации, а маршруты `text` и `files`, открываемые с главного экрана.

**Web сейчас:**
- События приходят в `SessionEventCallbacks`: `onTextReceived`, `onTextSnapshot`, `onFileOffer`, `onFileProgress`, `onFileSnapshot`, `onSessionLost`, `onReconnecting`.
- После каждого переподключения snapshot заново приносит всю ленту.
- `main.ts` связывает контроллеры через callbacks `render`.
- Защищённый режим определяется по `location.protocol === "https:"`.
- `document.title` нигде не меняется; исходный заголовок - «DeviceBridge - локальная связь».
- Ограничения:
  - privacy-контракт требует ровно одно упоминание `serviceWorker` и запрещает литералы `http(s)://` в собранных файлах;
  - CSP `default-src 'self'` запрещает `data:`-картинки, поэтому значок уведомления должен быть файлом того же origin.

## Goals / Non-Goals

**Goals:**
- Уведомления о событиях на телефоне и на странице по спецификации `event-notifications`, без новых сетевых маршрутов и без изменения протокола.
- Ни одного секрета и ни одного содержимого на экране блокировки телефона. Содержимое на компьютере показывается только по выбору человека.
- Минимальные изменения в координаторах: уведомления подписываются на существующие `StateFlow` и callbacks, а не встраиваются в бизнес-логику.

**Non-Goals:**
- Web Push, service worker, уведомления при закрытой вкладке.
- Собственные звуки, вибрация по шаблону, группы уведомлений по браузерам.
- Уведомления в Android-версии Chrome: `new Notification()` там недоступен без service worker.
- Подтверждение подключения из шторки.

## Decisions

### 1. Android: уведомления строятся из разницы состояний, а не из шины событий

`EventNotificationCoordinator` (новый файл в пакете `server`, singleton) на `@ApplicationScope` подписывается на три `StateFlow` и сравнивает каждый новый снимок с предыдущим. Так уже работает `FileSessionEventBridge`. Что он отслеживает:
- **запросы подключения:** новый `PendingBrowserRequest.id` означает показать уведомление, пропавший - снять;
- **входящие файлы:** появилась группа файлов `BROWSER_TO_ANDROID`, ждущих решения (`QUEUED` или `CONNECTING`), с одним `ownerSessionId`;
- **итоги:** все файлы группы одного `ownerSessionId` в одном направлении перешли в терминальную фазу, и в ней есть хотя бы один файл, ставший терминальным после предыдущей сводки. Повтор файла снова делает его нетерминальным, поэтому сводка покажется заново;
- **текст:** новый `TextMessageId` с направлением от браузера.

Первый снимок после запуска сервера служит базой и уведомлений не даёт.

Альтернатива - дописать вызовы уведомлений в `recordTerminal` координаторов или завести общую шину. Отклонена: это меняет три координатора и их тесты. Кроме того, запросы подключения и предложения файлов не имеют terminal-хуков.

Правила показа и тексты считает чистая модель `EventNotificationModelFactory`, по образцу `ServerNotificationModelFactory` и с тем же `safeNotificationName()`. Она покрывается JVM-тестами без Android. Публикацию в `NotificationManager` делает тонкий `AndroidEventNotificationPublisher`.

### 2. Android: видимость приложения через `ActivityLifecycleCallbacks`

`AppVisibilityTracker` регистрируется в `DeviceBridgeApplication` и считает запущенные Activity (`onStart`/`onStop`). Наружу он отдаёт `StateFlow<Boolean>`. Пока приложение видно, координатор не публикует новых уведомлений о событиях, но продолжает обновлять базу. Поэтому события, увиденные в приложении, не всплывают позже, когда человек его свернёт. Уже показанные уведомления о запросах и файлах снимаются по разрешению события, а не по открытию приложения.

Альтернатива - `ProcessLifecycleOwner` из `lifecycle-process`. Отклонена: это новая зависимость ради десятка строк, а приложение состоит из одной Activity.

### 3. Android: канал, идентификаторы, экран блокировки

- **Канал.** `devicebridge_events` «События», `IMPORTANCE_HIGH`, со значком на иконке. Создаётся идемпотентно при первой публикации.
- **Идентификаторы.** Базовый id - 3_000:
  - запрос подключения: база + hash от `PairingRequestId`, `setTimeoutAfter(оставшийся срок)`;
  - входящие файлы: одно уведомление на `ownerSessionId`, обновляется при изменении группы;
  - итоги: одно уведомление на `ownerSessionId` и направление;
  - текст: одно уведомление на сообщение, все с общим `setGroup("devicebridge_text")` и сводкой группы, если сообщений больше одного.
- **Экран блокировки.** Каждое уведомление имеет `VISIBILITY_PRIVATE` и `setPublicVersion` с общим заголовком без содержимого: «Запрос подключения», «Файлы с компьютера», «Текст с компьютера», «Передача завершена».
- **Остановка сервера.** Все уведомления о тексте, запросах и входящих файлах снимаются. Итоговые уведомления остаются: они не содержат ничего, кроме числа файлов, и полезны после автоостановки.

### 4. Android: действия уведомлений через неэкспортируемый `BroadcastReceiver`

`EventNotificationActionReceiver` объявляется с `android:exported="false"`. Его `PendingIntent` явные и `FLAG_IMMUTABLE`, extras содержат только id и никакого содержимого. Действия выполняются через `goAsync()` на app scope:
- **«Копировать».** Берёт текст по `TextMessageId` из `TextTransferRepository.state`, а не из extras, и кладёт его в `ClipboardManager`. Если сообщения уже нет, ничего не копирует и снимает уведомление.
- **«Принять».** Добавляет файлы группы в `NotificationAcceptedTransfers`: множество id, известных в момент нажатия, ждущих решения, одного `ownerSessionId`. `TrustedAutoAcceptController` получает третье основание для приёма, наравне с «доверенный браузер» и «продолжение». Путь приёма в папку по умолчанию один на все случаи, а файлы из `QUEUED` принимаются по мере продвижения в `CONNECTING`. Если папка стала недоступна, файл попадает в `paused`, и уведомление превращается в «Откройте приложение, чтобы выбрать папку».
- **«Отклонить».** Вызывает `cancel` для каждого ещё не начатого файла группы.

Кнопки, открывающие экран, - «Открыть» и «Показать», а также нажатие на само уведомление. Они сразу используют `PendingIntent.getActivity`: на Android 12+ receiver не может запускать Activity (запрет notification trampoline). «Открыть» для ссылки - это `getActivity` с `ACTION_VIEW` на ссылку, прошедшую `TextContentClassifier`. Экран в приложении выбирает extra `EXTRA_OPEN_SECTION` (`home`, `text`, `files`) в `MainActivity`. Он обрабатывается так же, как extra плитки: `onCreate` и `onNewIntent`, затем extra удаляется, затем `DeviceBridgeApp` делает навигацию через `LaunchedEffect`.

Альтернатива - действия через `ServerForegroundService`. Отклонена: сервис отвечает за lifecycle сервера, а смешивать его с обработкой уведомлений хуже для тестов.

### 5. Android: строка в настройках вместо своего переключателя

Своего переключателя «уведомления о событиях» нет: канал Android уже даёт включить, выключить и выбрать звук. В разделе «Сервер» появляется строка «Уведомления о событиях»:
- если всё включено, строка показывает «Включены»;
- если канал или разрешение выключены, - «Выключены в системе»;
- по нажатию открывается `ACTION_CHANNEL_NOTIFICATION_SETTINGS`, а если нет разрешения, - `ACTION_APP_NOTIFICATION_SETTINGS`.

Двойной выключатель (свой и системный) запутал бы человека.

### 6. Web: `notificationController` с внедряемыми портами

Новый модуль `eventNotificationController.ts` не знает о `SessionController`, `TextTransferController` и `FileTransferController`, по тому же правилу независимости, что `themeController`. Он получает события через методы:
- `textReceived(item, {live})`;
- `filesOffered(items)`;
- `uploadFinished(item)`;
- `connectionLost()`.

Окружение внедряется портами:
- `NotificationPort`: `permission`, `requestPermission()`, `show(title, {body, tag, icon})`, возвращающий handle с `onclick` и `close`;
- `VisibilityPort`: `isAttentionElsewhere()` = `document.hidden || !document.hasFocus()` и подписка на `visibilitychange`, `focus`, `blur`;
- `TitlePort`.

Так контроллер тестируется в node и jsdom, где `Notification` нет. Обвязка в `main.ts` оборачивает существующие `render` callbacks и callbacks сокета.

**Что считается новым:**
- `text.received` и `file.offer` - всегда живые события;
- snapshot после переподключения уведомляет только о тех id, которых контроллер ещё не видел;
- первый snapshot после загрузки страницы - база.

Множество увиденных id живёт в памяти контроллера и ограничено 500 записями.

**Потеря связи.** Уведомление показывается один раз при переходе из `connected` или `reconnecting` в `needsUserAction`, `sessionLost` или `offline`. Переход в `reconnecting` уведомления не даёт.

**Объединение.** Одинаковый `tag` на вид события (`devicebridge-text`, `devicebridge-files`, `devicebridge-upload`, `devicebridge-connection`). Новое уведомление заменяет прежнее, а текст сообщает «и ещё N». Счётчик N сбрасывается, когда человек возвращается на вкладку.

**Клик.** `window.focus()`, `close()`, прокрутка к `[data-message-id]` или `[data-transfer-id]` и фокус на карточке.

### 7. Web: доступность и настройки

- **Когда доступно.** Системные уведомления доступны, только если `location.protocol === "https:"` и `"Notification" in globalThis`. `isSecureContext` не используется: `http://127.0.0.1` при разработке считается защищённым, а продукт на `http://IP` - нет. Поведение должно совпадать.
- **Хранение настроек.** Хранилище `browserNotificationPreferenceStore.ts` по образцу `browserSecurityWarningPreferenceStore`: ключ `devicebridge.notifications.v1`, запись `{version: 1, enabled, hideContent}`. Неверная запись удаляется, а при ошибке хранилища действует значение по умолчанию: выключено, содержимое показывается.
- **Интерфейс.** Панель «Уведомления» в колонке `.shell-layout__connection` после пометок о безопасности. Состояния панели:
  - `unavailable` (HTTP): подсказка «Уведомления доступны в защищённом режиме»;
  - `default`: кнопка «Включить уведомления»;
  - `enabled`: «Уведомления включены», переключатели «Скрывать содержимое» и «Выключить»;
  - `denied`: объяснение, как разрешить через значок слева от адреса.

  Кнопка темы и её контракты не трогаются.
- **Текст уведомления.** Задаётся через `body` и `title`. Браузер выводит их как текст, HTML не интерпретируется. Начало текста ограничено 120 символами, имя файла - 64 символами после удаления управляющих и bidi-символов.

### 8. Web: значок уведомления

Значок берётся во время работы из `link[rel="icon"]`. Это уже собранный `/assets/favicon-*.svg` того же origin, поэтому ни CSP, ни privacy-контракт не страдают. Импортировать SVG из TS нельзя: Vite встроит его как `data:` с литералом `http://www.w3.org`. Если ручная проверка покажет, что Chrome или Edge на Windows не рисуют SVG в уведомлении, добавляется PNG 96×96 через `?url` с отключённым встраиванием для этого файла. Решение фиксируется в задаче проверки.

### 9. Web: счётчик в заголовке

`TitlePort` хранит исходный `document.title` при старте. Пока внимание не на вкладке, каждое уведомляемое событие увеличивает счётчик, и заголовок становится `(N) <исходный>`. Возврат на вкладку сбрасывает счётчик и заголовок. Счётчик работает и без разрешения на уведомления, и по HTTP.

## Risks / Trade-offs

- **[Chrome выгружает давно скрытые вкладки (Memory Saver)]** → уведомления перестают приходить до возвращения на вкладку. Смягчение: в подсказке панели сказать, что вкладка должна оставаться открытой. Открытый WebSocket обычно удерживает вкладку от заморозки. Проверяется вручную на часовом простое.
- **[Windows «Не беспокоить» или «Фокусировка» скрывает уведомления]** → это ожидаемое поведение системы, страница его не обходит.
- **[Повторное уведомление после перезагрузки страницы]** → первый snapshot служит базой, поэтому события, пришедшие до загрузки, не уведомляются. Их видно на странице и в счётчике ленты.
- **[«Принять» из шторки при потере доступа к папке]** → файл уходит в `paused`, и уведомление предлагает открыть приложение. Файл не принимается «куда-нибудь».
- **[Текст в буфере обмена телефона]** → Android 13+ показывает системное подтверждение копирования. Содержимое текста не пишется в extras `PendingIntent`.
- **[Много текстов подряд на телефоне]** → группа с одной сводкой. Android сам сворачивает группу больше 4 уведомлений.
- **[Существующие контракты]** → `ServerManifestContractTest` и `ServerManifestInstrumentedTest` сейчас запрещают receiver загрузки. Новый receiver не экспортируется и не слушает системные события, контракт уточняется, а не ослабляется. Контракт `androidPublisherUsesIdempotentLowPriorityChannel...` остаётся верен, потому что события публикуются из отдельного файла.
