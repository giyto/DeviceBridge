# embedded-server-viability Specification

## Purpose

Определить проверяемые условия, при которых Ktor 3.5.2 с engine CIO может быть принят как встроенный локальный сервер единственного Android-приложения DeviceBridge.

## ADDED Requirements

### Requirement: Диагностический сервер изолирован от пользовательской release-сборки

Система MUST предоставлять прототип сервера и средства управления им только в debug-варианте. Диагностические маршруты MUST использовать префикс /diagnostics и MUST NOT пересекаться с зарезервированным production-префиксом /api/v1.

#### Scenario: Debug-сборка предоставляет harness

- **WHEN** разработчик запускает debug-сборку
- **THEN** доступен диагностический экран запуска и остановки сервера
- **AND** экран показывает состояние, адрес, порт и последнюю ошибку

#### Scenario: Release-сборка не раскрывает диагностику

- **WHEN** собирается release-вариант приложения
- **THEN** в нём отсутствуют диагностический экран, диагностический токен и маршруты /diagnostics/*
- **AND** сервер нельзя запустить через диагностическую точку входа

### Requirement: Сервер имеет управляемый и повторяемый жизненный цикл

Диагностический controller MUST явно представлять состояния Stopped, Starting, Running, Stopping и Error и MUST освобождать порт, coroutine scope и соединения после остановки.

#### Scenario: Двадцать циклов запуска и остановки

- **WHEN** instrumented-тест последовательно выполняет 20 циклов start → health-check → stop
- **THEN** каждый запуск завершается состоянием Running
- **AND** каждый health-check успешен
- **AND** после каждой остановки состояние становится Stopped и порт освобождается

#### Scenario: Ошибка привязки порта

- **WHEN** сервер не может занять выбранный порт
- **THEN** controller переходит в Error с понятной диагностикой
- **AND** после устранения конфликта новый запуск возможен без перезапуска приложения

### Requirement: Сервер доступен локально с компьютера

Сервер MUST привязываться к локальному интерфейсу так, чтобы диагностический запрос мог быть выполнен с компьютера. Для AVD допускается воспроизводимый adb port forwarding. Диагностический трафик MUST оставаться локальным и MUST NOT обращаться к внешнему backend.

#### Scenario: Проверка с компьютера через AVD

- **WHEN** сервер запущен на AVD и настроен документированный adb port forwarding
- **THEN** авторизованный health-check с компьютера получает ответ от Android-приложения

#### Scenario: Разрешение локальной сети на API 37.1

- **WHEN** debug-приложение с targetSdk 37 запускает LAN-проверку на API 37.1
- **THEN** оно объявляет и запрашивает ACCESS_LOCAL_NETWORK до сетевого доступа
- **AND** отказ пользователя отображается как контролируемая ошибка, а не crash

### Requirement: HTTP health-check требует диагностическую авторизацию

Сервер MUST предоставлять GET /diagnostics/health и принимать только запросы с активным случайным диагностическим bearer-токеном, существующим в памяти текущего запуска.

#### Scenario: Авторизованный health-check

- **WHEN** клиент отправляет действующий токен
- **THEN** сервер возвращает HTTP 200 и JSON со status=ok, версией Ktor, engine, API устройства и uptime

#### Scenario: Запрос без действующего токена

- **WHEN** токен отсутствует или неверен
- **THEN** сервер возвращает HTTP 401
- **AND** ответ не раскрывает диагностические данные

### Requirement: WebSocket сохраняет порядок и целостность сообщений

Сервер MUST предоставлять /diagnostics/ws и возвращать авторизованному клиенту каждое принятое диагностическое сообщение без изменения идентификатора и payload.

#### Scenario: Тысяча последовательных сообщений

- **WHEN** клиент отправляет 1000 сообщений с последовательными идентификаторами
- **THEN** клиент получает ровно 1000 ответов
- **AND** порядок, идентификаторы и payload полностью совпадают

#### Scenario: Аварийное отключение клиента

- **WHEN** WebSocket-клиент разрывает соединение без штатного close
- **THEN** сервер освобождает ресурсы сессии
- **AND** новый клиент может подключиться и успешно обменяться сообщением

### Requirement: Передача 500 МБ выполняется потоково

Сервер MUST принимать и отдавать детерминированный поток размером 500 МБ без загрузки полного payload в память. Целостность MUST проверяться инкрементальным SHA-256.

#### Scenario: Потоковая загрузка на сервер

- **WHEN** клиент отправляет 500 МБ в /diagnostics/upload
- **THEN** сервер обрабатывает поток частями, не сохраняет его как единый ByteArray или файл пользователя
- **AND** возвращает фактический размер и совпадающий SHA-256
- **AND** процесс не завершается с OOM

#### Scenario: Потоковое скачивание с сервера

- **WHEN** клиент запрашивает 500 МБ из /diagnostics/download
- **THEN** сервер генерирует и отправляет данные частями
- **AND** клиент получает ровно 500 МБ с ожидаемым SHA-256
- **AND** процесс не завершается с OOM

#### Scenario: Отмена потока

- **WHEN** клиент отменяет upload или download до завершения
- **THEN** операция прекращается
- **AND** соединение, coroutine и буферы освобождаются
- **AND** следующий health-check остаётся успешным

### Requirement: Результат spike воспроизводим и блокирует неверный стек

Проект MUST содержать отчёт с одинаковой матрицей проверок для API 29 и API 37.1, версиями Ktor/engine, ABI и образом AVD, командами запуска, результатами HTTP/WebSocket/streaming/lifecycle, метриками памяти и изменением размера APK.

#### Scenario: Ktor/CIO принят

- **WHEN** все обязательные проверки проходят на API 29 и API 37.1
- **AND** 500 МБ не буферизуются пропорционально размеру payload
- **AND** release-сборка не раскрывает диагностику
- **THEN** отчёт фиксирует verdict=accept и обоснование

#### Scenario: Обязательная проверка не пройдена

- **WHEN** хотя бы одна обязательная проверка не проходит воспроизводимо на любом целевом API
- **THEN** отчёт фиксирует verdict=replace с причиной
- **AND** дальнейшая разработка production-сервера на этом adapter блокируется до отдельного change по его замене
