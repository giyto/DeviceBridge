## Context

См. `proposal.md` — проект является стандартным Android-приложением на Kotlin и Compose, а окончательное ТЗ фиксирует один APK со встроенным сервером и web-интерфейсом для браузера компьютера. Сейчас весь экран находится в `MainActivity`; Navigation Compose, ViewModel-слой и границы Clean Architecture отсутствуют. Этот change создаёт только Android-каркас, не запуская локальный сервер и не добавляя web-ресурсы.

## Goals / Non-Goals

**Goals:**

- получить тестируемую точку входа Compose;
- отделить навигацию, presentation state и feature-экраны от Activity;
- задать направление зависимостей `app -> feature -> domain` и вынести общие UI-компоненты в `core/ui`;
- подготовить точки расширения для embedded server, pairing с браузером, истории и настроек;
- отображать только состояние «Сервер остановлен», не имитируя адрес, код или подключённый браузер.

**Non-Goals:**

- многомодульная Gradle-архитектура;
- embedded server, web UI, локальный протокол, сетевые разрешения и foreground service;
- pairing, передача данных и постоянное хранилище;
- отдельное desktop-приложение;
- визуально завершённый production-дизайн всех будущих функций.

## Decisions

### Один Gradle-модуль с границами Clean Architecture

На первом этапе сохраняется единственный Gradle-модуль `app`. Внутри него `app` отвечает за composition root и навигацию, `feature/<name>` — за экраны, ViewModel и UI state, `domain` — за платформенно-независимые модели и правила, `core/ui` — за действительно переиспользуемые Compose-компоненты. Направление зависимостей: feature может зависеть от domain и core, а domain не зависит от Android и feature.

Пакет `data` предусмотрен итоговой архитектурой, но не создаётся пустым: он появится вместе с первым реальным server или storage adapter. Новые пакеты также создаются только при наличии реального класса с соответствующей ответственностью.

Альтернатива — сразу создать отдельные Gradle-модули `core`, `domain`, `data` и feature. Она отклонена как преждевременная; разделение на модули рассматривается только при измеримой проблеме сборки или повторного использования.

### Navigation Compose для верхнеуровневых экранов

Корневой `DeviceBridgeApp` владеет `NavHost`, а `MainActivity` только устанавливает тему и вызывает корневой composable. Маршруты описываются типобезопасной закрытой моделью, чтобы строки маршрутов не распространялись по UI.

Альтернатива — переключать экраны локальным `remember`-состоянием. Она отклонена, потому что pairing и transfer flows потребуют back stack и восстановления состояния.

### MVVM и неизменяемое состояние серверной сессии

Главный экран получает неизменяемый `ServerSessionUiState` из ViewModel через `StateFlow`. В этом change поддерживается только честное состояние `Stopped`; последующие changes расширят модель состояниями запуска сервера, ожидания браузера, активной сессии и ошибки. Доступность действий «Текст» и «Файлы» вычисляется из состояния, а не задаётся непосредственно в composable.

Однонаправленный поток имеет форму `UiAction -> ViewModel -> UiState -> Compose`. В первом change действия запуска сервера и передачи не обрабатываются: соответствующие элементы disabled и объясняют будущую последовательность «запустить сервер — подключить браузер».

Альтернатива — хранить набор независимых флагов `isServerRunning`, `hasBrowser`, `isLoading` и `hasError`. Она отклонена из-за возможности противоречивых комбинаций.

### Тесты поведения отдельно от визуальных проверок

Правила доступности действий и начальное состояние проверяются быстрыми unit-тестами. Compose UI-тесты проверяют наблюдаемую навигацию, тексты, selection state, disabled state и отсутствие фиктивных сетевых данных. Previews и ручные проверки покрывают светлую/тёмную тему, увеличенный шрифт и TalkBack semantics.

## Risks / Trade-offs

- **Риск:** package boundaries внутри одного модуля могут стать только формальностью. → Domain не импортирует Android/Compose, feature-пакеты не импортируют друг друга, а новые общие абстракции появляются только после второго реального использования.
- **Риск:** состояние «Сервер остановлен» может восприниматься как уже работающая серверная функция. → Кнопка запуска в этом change недоступна, интерфейс явно сообщает, что подключение появится на следующем этапе.
- **Риск:** временные экраны могут восприниматься как законченная функциональность. → История и настройки показывают честные пустые состояния без тестовых данных.
- **Компромисс:** настройка ViewModel и навигации добавляет кода до появления сети. → Это уменьшает объём переработки во всех последующих changes.

## Migration Plan

1. Зафиксировать успешную исходную сборку и добавить зависимости навигации/ViewModel.
2. Добавить падающие unit- и Compose UI-тесты требуемого поведения.
3. Создать app shell, минимальные package boundaries и feature-экраны.
4. Перевести `MainActivity` на корневой `DeviceBridgeApp`.
5. Удалить шаблонный composable только после прохождения тестов на API 29 и API 37.1.

Откат выполняется возвратом одного change-коммита; пользовательские данные и внешние API отсутствуют.
