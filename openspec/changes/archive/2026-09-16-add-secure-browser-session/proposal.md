## Why

Работающий LAN server уже доступен любому участнику той же сети, но ещё не отличает браузер владельца от постороннего клиента и не предоставляет защищённую сессию для будущих операций. Следующий этап ТЗ должен добавить проверяемый pairing с подтверждением на телефоне до реализации передачи пользовательских данных.

## What Changes

- При каждом явном запуске сервера создаётся одноразовый шестизначный код с временем жизни не более пяти минут; после использования или истечения код заменяется.
- Browser client начинает pairing через production `/api/v1/session/*`, вводит код и ожидает отдельного решения пользователя на Android host.
- Android UI показывает попытку подключения с понятной информацией о клиенте и позволяет явно разрешить или отклонить её.
- После разрешения сервер выдаёт криптографически случайный session bearer token не менее 128 бит, который не помещается в URL, журналы или web assets.
- Пять неверных попыток для одного клиента приводят к временной блокировке; истёкший код, отказ пользователя и блокировка имеют разные безопасные ответы и понятные состояния UI.
- Все production HTTP API, кроме web assets, web manifest и начала pairing, требуют действующий token. WebSocket требует авторизации первым протокольным сообщением до выдачи событий.
- Android host показывает фактические активные browser sessions, позволяет немедленно отключить каждую из них, а остановка сервера, смена сети или отзыв разрешения аннулируют все session tokens.
- Browser UI получает экран кода, ожидание подтверждения, подключённое состояние и обработку отказа, истечения, блокировки, отзыва и потери сессии.
- Session token ограничен текущим server lifecycle. Постоянное доверие браузеру, encrypted trusted-browser tokens и управление ими в настройках остаются этапом `add-local-history-and-settings`.
- Передача текста, ссылок и файлов остаётся недоступной до следующих changes и не имитируется после успешного pairing.

## Capabilities

### New Capabilities

- `secure-browser-session`: одноразовый pairing, подтверждение на телефоне, выпуск и проверка session token, ограничение попыток, отзыв и завершение browser session.

### Modified Capabilities

- `android-app-shell`: главный экран показывает код, запрос подтверждения и список активных браузеров, сохраняя transfer-действия недоступными до их отдельных changes.
- `browser-web-interface`: статическая страница получает настоящий pairing flow и авторизованный статус, но ещё не предоставляет передачу данных.
- `server-lifecycle`: production server публикует только завершённые session/status/events routes, защищает их token и аннулирует сессии вместе с lifecycle.

## Impact

- Затрагиваются domain-модели и use cases сессий, application-scoped coordinator, Hilt composition root, Ktor production routes, Android Compose UI и foreground notification.
- Web-клиент получает протокольные DTO, pairing state machine и same-origin вызовы session API/WebSocket; Vite pipeline и offline-поставка внутри APK сохраняются.
- Секреты текущего lifecycle хранятся только в памяти Android process; browser token ограничивается текущей вкладкой/сеансом хранения и удаляется после отказа сервера. Android Keystore и постоянные trusted-browser credentials в этот change не входят.
- Новые тесты покрывают API 29/API 37.1, неверный и истёкший код, rate limit, approve/deny/revoke, запросы без token, HTTP/WebSocket authorization, остановку/смену сети и Chrome/Edge pairing в локальной сети.
- Архитектурная граница не меняется: устанавливается одно Android-приложение, отдельный desktop client, аккаунт, внешний backend и арендуемая инфраструктура не добавляются.
