## Context

Мотивация описана в proposal.md. Здесь только текущее состояние, которое определяет подход.

- `KtorServerRuntimeFactory` запускает `embeddedServer(CIO, host = 0.0.0.0, port = 8787)`. `allowedAuthorities` = `IP:порт`. Адрес клиента берётся из `call.request.local.remoteHost` через `RemoteClientAddress.canonicalIpv4`. Смена сети уже перезапускает сервер (`networkFingerprint`).
- Ktor CIO 3.5.2 не поддерживает TLS на стороне сервера: в `ktor-server-cio-jvm` нет TLS-кода, а `sslConnector` работает только в Netty, Jetty и Tomcat. `ktor-network-tls` есть только для клиента.
- `SessionRequestSecurityPolicy.validateSameOrigin` и `WebRoutes.isAllowedWebRequest` жёстко требуют `Origin` со схемой `http`. `ServerEndpoint.url` жёстко собирает `http://`.
- Web-клиент уже готов к HTTPS в нескольких местах. `sessionEventSocketClient` выбирает `wss:` по `location.protocol`, `clipboardWriter` проверяет `isSecureContext`. Авторизация идёт через `Authorization: Bearer`, cookie не используются. Доверенный credential браузера лежит в `localStorage`, а он привязан к origin.
- Системные настройки хоста (хранилище сертификатов Windows) при разработке и в E2E менять нельзя.

## Goals / Non-Goals

**Goals:**
- Настоящий HTTPS без предупреждений после одной установки корня на компьютер.
- Сохранить CIO и все существующие маршруты без изменений протокола.
- Режим выключаемый и изолированный: в HTTP-режиме поведение и производительность не меняются.

**Non-Goals:**
- Системные уведомления на компьютере, PWA и service worker: отдельные change поверх защищённого контекста.
- mDNS-объявление `devicebridge.local`: имя только включается в сертификаты заранее.
- Сертификаты публичного центра, собственный домен, ACME.
- Взаимная TLS-аутентификация браузера (client certificates).

## Decisions

### 1. TLS-приёмник перед CIO, а не смена движка

В защищённом режиме CIO слушает только `127.0.0.1` на случайном порту. На публикуемом LAN-порту работает свой приёмник на платформенном TLS (Conscrypt через `SSLContext`): он расшифровывает соединение и перекачивает байты в CIO и обратно. Двунаправленная перекачка идёт на `Dispatchers.IO` с буфером 64 КиБ.

- *Альтернатива: движок Netty с `sslConnector`.* Добавляет несколько мегабайт, на Android у Netty известные проблемы (`Unsafe`, нативный транспорт), а все серверные тесты и настройки таймаутов написаны под CIO. Отклонено.
- *Альтернатива: Jetty/Tomcat* на Android не поддерживаются.
- *Альтернатива: шифрование приложением поверх HTTP* не защищает от подмены JavaScript и не даёт защищённого контекста (см. proposal.md). Отклонено.

HTTP-режим не использует приёмник вовсе: CIO слушает `0.0.0.0` как сейчас.

### 2. HTTP и TLS на одном порту через первый байт

Приёмник принимает обычный `ServerSocket` и читает первый байт, возвращая его в `PushbackInputStream`. `0x16` означает TLS ClientHello: соединение расшифровывается через `SSLEngine` с собственным блокирующим циклом wrap/unwrap (`TlsEngineStreams`). Любой другой байт означает обычный HTTP: соединение перекачивается в CIO как незащищённое.

- *Отклонено по итогам спайка:* `SSLSocketFactory.createSocket(socket, consumed, autoClose)`. Метод есть в JDK, но не входит в публичный Android SDK (компилятор его не видит), и поддержка в Conscrypt не гарантирована. `SSLEngine` одинаково работает в JDK (JVM-тесты) и Conscrypt (эмулятор).
- *Альтернатива: отдельный порт для HTTP-страницы установки.* Тогда старая закладка `http://IP:8787` падает с «пустым ответом» вместо понятной страницы. Отклонено.

### 3. Реестр соединений: адрес клиента и признак TLS

Приёмник подключается к CIO с локального сокета и записывает `локальный порт → (IPv4 клиента, secure)` в потокобезопасный реестр. При закрытии соединения запись удаляется. В защищённом режиме `sourceIpv4` и проверка схемы получают данные из реестра по `call.request.local.remotePort`.

- Соединение к CIO, которого нет в реестре (другое приложение на телефоне подключилось к loopback-порту напрямую), получает 403 и закрывается.
- Для незащищённых соединений Ktor-перехватчик разрешает только `GET /`, ассеты страницы установки, `GET /devicebridge-ca.crt` и отдаёт `308` на `https://` для остальных путей верхнего уровня. API, WebSocket, text и file маршруты отвечают 403.
- Проверки `Origin` получают ожидаемую схему (`http` или `https`) от runtime, вместо константы `"http"`.

### 4. Сертификаты: свой X.509-кодировщик и AndroidKeyStore

- **Корень:** EC P-256. Ключ в AndroidKeyStore (`PURPOSE_SIGN`, неэкспортируемый, alias `devicebridge_tls_ca`). Сертификат строится собственным минимальным DER/X.509-кодировщиком (`data/tls`): `basicConstraints CA:true, pathLen 0` (critical), `keyUsage keyCertSign|cRLSign`, `nameConstraints` (critical) с permitted `iPAddress` 10/8, 172.16/12, 192.168/16 и `dNSName devicebridge.local`. Срок 10 лет. Подпись TBS-структуры выполняет платформенный `Signature("SHA256withECDSA")` с ключом из AndroidKeyStore; кодировщик только упаковывает поля.
- **Сертификат сервера:** EC P-256, ключ тоже в AndroidKeyStore (alias `devicebridge_tls_leaf`), новый при каждом перевыпуске. Поля: `basicConstraints CA:false`, `keyUsage digitalSignature`, `extendedKeyUsage serverAuth`, SAN `IP:<LAN IPv4>` и `DNS:devicebridge.local`. `notBefore` = сейчас − 24 ч (запас на расхождение часов ПК), срок 30 дней. Перевыпуск при старте сервера, если адреса нет в SAN или осталось меньше 7 дней.
- **Хранение:** DER корня и сертификата сервера лежат в `noBackupFilesDir/tls/`, ключи — в AndroidKeyStore. Всё это исключено из резервного копирования: ключи всё равно непереносимы.
- **Интерфейс для тестов:** `TlsKeyStore` с реализациями AndroidKeyStore и программной (JVM-тесты). Генерация и цепочка проверяются в JVM через `CertPathValidator` (PKIX), который соблюдает name constraints.
- *Альтернатива: BouncyCastle (`bcpkix`).* В release выключен R8 (`optimization.enable = false`), поэтому библиотека вошла бы целиком: jar-файлы ~10,4 МБ, APK вырос бы на 8–10 МБ при текущих 33 МБ. Нам нужны только два фиксированных профиля сертификата. Отклонено.
- *Альтернатива: `ktor-network-tls-certificates` (`buildKeyStore`).* Не умеет name constraints и CA-расширения. Отклонено.
- **Риск своего кодировщика** (ошибка ASN.1 ломает доверие незаметно) закрывается тестами: строгий разбор `CertificateFactory` JDK, `CertPathValidator` (PKIX с name constraints), эталонные байты полей и настоящее TLS-рукопожатие через Conscrypt на эмуляторе.

### 5. Отпечаток в формате окна Windows

Окно предупреждения Windows при установке корня показывает `Thumbprint (sha1)` группами по 8 заглавных hex-символов. Телефон показывает SHA-1 в том же формате и SHA-256 под «Подробнее». Страница установки просит сверить именно с экраном телефона, так как сама страница пришла по HTTP.

### 6. Страница установки: отдельная точка входа Vite

`setup.html` собирается Vite как вторая точка входа (свой маленький TS-модуль и общий CSS). Сервер отдаёт её со своим CSP. В этом CSP `connect-src` дополнительно разрешает точный `https://IP:порт`, чтобы страница могла проверить доверие: `fetch("https://IP:порт/api/v1/tls-probe", {mode: "no-cors"})`. Если fetch прошёл, цепочка доверена, и страница делает `location.replace` на HTTPS. `tls-probe` отвечает `204` без авторизации и только по TLS. ОС для инструкции выбирается по `navigator.userAgent`, остальные вкладки остаются доступны.

### 7. Переключение режима через lifecycle сервера

Флаг `secureModeEnabled` добавляется в `DeviceSettings` и хранилище настроек (по умолчанию `false`). `KtorServerRuntimeFactory.create()` читает флаг при запуске. Переключение и сброс при работающем сервере выполняются через существующий путь остановки и запуска, после подтверждения в UI. `ServerEndpoint` получает поле `secure`, от которого зависит `url`.

### 7a. Входной адрес всегда `http://`

Телефон и уведомление показывают `http://IP:порт` и в защищённом режиме. Предупреждение браузера об ошибке сертификата появляется до загрузки любой страницы, поэтому сервер не может ничего объяснить человеку, открывшему `https://` без установленного корня. Адрес `http://` на том же порту ведёт на страницу установки, а при доверенном корне страница сама переходит на HTTPS (решение 6). `ServerEndpoint.url` поэтому всегда `http://`, а признак `secure` управляет пояснением в UI.

- *Альтернатива: показывать `https://`.* Первое же открытие без сертификата — красный экран, и люди нажимают «Всё равно перейти», после чего браузер молча принимает любой сертификат для этого адреса. Проверено на Яндекс Браузере. Отклонено.

### 7b. Передача сертификата без сети

«Поделиться сертификатом» записывает DER корня в `cacheDir/shared-certificate/DeviceBridge-CA.crt` и отдаёт его через `FileProvider` в `Intent.ACTION_SEND` с типом `application/x-x509-ca-cert`. Файл идёт через канал, которому человек доверяет (мессенджер, почта, USB), а не по незащищённому Wi-Fi, поэтому подмену исключает сам канал.

### 7c. Как HTTPS-страница узнаёт, что сертификат не установлен

Ошибку сертификата при открытии `https://` показывает сам браузер до того, как сервер отправит хоть байт, поэтому переадресовать оттуда нельзя. Но после «Всё равно перейти» страница уже загружена, и её можно предупредить. JavaScript не может спросить о доверии напрямую, а `isSecureContext` остаётся `true` (проверено). Косвенный признак в Chromium (Chrome, Edge, Яндекс Браузер): регистрация service worker на таких страницах отклоняется с сообщением «An SSL certificate error occurred when fetching the script», а при доверенном сертификате — по другой причине. Страница вызывает `navigator.serviceWorker.register("/web-manifest.json", {scope: "/assets/"})`: JSON с типом `application/json` не может стать service worker, поэтому регистрация не происходит никогда, а текст отказа говорит о доверии. Любой иной исход считается «не определено» и предупреждения не даёт (Firefox, Safari).

- Страница установки по ссылке из предупреждения получает `?untrusted=1` и не проверяет доверие: запомненное исключение браузера пропускает и `no-cors`-проверку, и страница увела бы обратно на HTTPS. Вместо этого она просит установить сертификат и полностью перезапустить браузер, что сбрасывает исключение.
- Правило release-политики `SERVICE_WORKER` и web-контракт приватности допускают только этот вызов с аргументом `/web-manifest.json`; любой другой `register(` по-прежнему запрещён.
- *Альтернатива: `isSecureContext` или `crypto.subtle`.* Оба доступны и после обхода предупреждения (проверено в Chrome). Отклонено.

### 8. Web: вариант предупреждения по схеме страницы

`securityWarningController` выбирает вариант по `location.protocol === "https:"`. На HTTPS вместо предупреждения выводится компактная пометка «Соединение зашифровано» без сворачивания. Сохранённый preference сворачивания по-прежнему относится только к HTTP-варианту.

### 9. Ограничения приёмника

- Не больше 64 одновременных соединений: лишние закрываются сразу.
- Таймаут на рукопожатие и первый байт — 10 с (`soTimeout` на время рукопожатия, затем снимается, чтобы долгие передачи и WebSocket не рвались).
- Протоколы `TLSv1.3` и `TLSv1.2`, наборы шифров по умолчанию Conscrypt.
- Остановка runtime закрывает `ServerSocket`, все активные пары сокетов и CIO.

## Risks / Trade-offs

- [Chrome или Firefox не соблюдают name constraints в корне, установленном пользователем] → Ключ корня неэкспортируем и не покидает телефон, поэтому ограничение — второй рубеж защиты. Java PKIX проверяется JVM-тестом. Поведение Chrome и Edge проверяется вручную на компьютере пользователя с его согласия: автоматический E2E не может менять хранилище хоста, а флаг SPKI подавляет и ошибки ограничений.
- [Ошибка в собственном DER-кодировании] → Сверка с JDK-парсером, PKIX-валидатором и TLS-рукопожатием на Android; кодируются только фиксированные поля, произвольного ввода нет.
- [Conscrypt не поддерживает `createSocket` с уже прочитанными байтами] → Запасной вариант на `SSLEngine` (решение 2), выбор делает спайк.
- [На Android `InetAddress.getLoopbackAddress()` в процессе приложения — это `::1`, а CIO слушает `127.0.0.1`; найдено сквозной проверкой] → Приёмник подключается к явному IPv4 `TlsFrontDoor.BACKEND_HOST`, CIO слушает тот же адрес, device-тест слушает его же.
- [Браузер помнит «Всё равно перейти» и помечает страницу «broken HTTPS» даже после установки корня; найдено при ручной проверке в Яндекс Браузере] → Телефон показывает входной адрес `http://` (решение 7a), страница установки предупреждает не нажимать «Всё равно перейти». Ручная проверка: Edge и Яндекс Браузер после установки корня открывают страницу без предупреждений.
- [Instrumented-тесты работают в процессе приложения и делят с ним AndroidKeyStore; тест с теми же именами ключей испортил корень приложения на эмуляторе] → Имена ключей — параметры `LocalCertificateAuthority`, device-тест использует свои. Приложение при этом корректно показало «Сертификат повреждён» и предложило сброс.
- [Перекачка через loopback снижает скорость больших файлов] → Буферы 64 КиБ и аппаратный AES-GCM. Замер на Xiaomi 22081212UG (Android 15) по Wi-Fi, файл 1 ГиБ через Chrome: на телефон HTTP 26,5 МиБ/с, HTTPS 25,3 МиБ/с (95 %); с телефона HTTP 26,2 МиБ/с, HTTPS 25,2 МиБ/с (96 %). Цель 70 % достигнута с запасом.
- [AndroidKeyStore на части устройств работает с ошибками] → Ошибка показывается как recoverable с кнопкой «Сбросить сертификат». Тихого отката на HTTP нет.
- [После перехода на HTTPS браузер «забывает» запомненное подключение, потому что `localStorage` привязан к origin] → Один повторный вход по коду. Об этом сказано в тексте переключателя. Доверенные записи на телефоне остаются.
- [Пользователь устанавливает корень, скачанный по подменённому HTTP] → Сверка отпечатка с экраном телефона и явный текст инструкции.
- [В E2E нельзя менять хранилище сертификатов Windows] → Chrome запускается с флагом `--ignore-certificate-errors-spki-list=<SPKI тестового корня>` на отдельном профиле: это доверие только этому ключу и только в тестовом процессе.
- [Firefox использует своё хранилище] → Отдельная вкладка инструкции (Настройки → Сертификаты → Импорт → «Доверять для сайтов»).

## Migration Plan

- Новый флаг по умолчанию `false`, поэтому у существующих пользователей ничего не меняется до явного включения.
- Откат для пользователя — выключить режим: сервер возвращается на HTTP, корень сохраняется для повторного включения.
- Откат релиза: флаг и файлы в `noBackupFilesDir/tls/` игнорируются старой версией. Ключи в AndroidKeyStore остаются до удаления приложения и безвредны.
