## Context

Мотивация описана в proposal.md. Здесь только то, что определяет способ реализации.

- **Адрес.** `ServerEndpoint(host, port, secure)` строит `url = "http://$host:$port"` из единственного частного IPv4, который выбрал `LanEndpointResolver`. Главный экран и уведомление сервера показывают этот `url`. Плитка адрес не показывает.
- **Проверка Host.** `KtorServerRuntimeFactory` один раз записывает `allowedAuthorities = setOf("$ip:$port")`. Этот набор используют все проверки Host и Origin: `SessionRequestSecurityPolicy`, `WebRoutes.isAllowedWebRequest`, `SecureModeGuard` и WebSocket в `SessionRoutes`. Перенаправление на HTTPS и CSP страницы установки строятся из заголовка Host запроса, поэтому работают с любым разрешённым именем без правок.
- **Смена сети.** `ServerLifecycleCoordinator.observeNetwork()` останавливает сервер при потере сети или смене адреса.
- **Сертификаты.** Они собираются вручную в DER (`Der.kt`, `X509Profiles.kt`). У корня name constraints: три частных диапазона IPv4 и dNSName `devicebridge.local`. SAN сертификата сервера всегда содержит `devicebridge.local`. Метод `covers()` проверяет только IP.
- **mDNS.** Кода mDNS, `MulticastLock` и разрешения `CHANGE_WIFI_MULTICAST_STATE` в проекте нет. У `NsdManager` нет публичного способа зарегистрировать своё имя хоста: `setHostname` скрыт, а `getHostname` появился только в API 36 и лишь читает имя. minSdk 29.
- **Уведомление о запросе подключения.** Сейчас у него только действие `OPEN`. Действия отправляются в `EventNotificationActionReceiver` через `EventNotificationRegistry` по числовому id. Коды запросов уведомлений считаются по формуле `id * ACTION_SLOTS(8) + ordinal`, `CONTENT_SLOT = 7`. В перечислении уже 6 действий.
- **Web.** `sessionEventSocketClient` делает 3 переподключения, а затем `SessionController` показывает `needsUserAction`. При загрузке страницы тоже 3 попытки (`RETRY_DELAYS_MS`), затем `offline` без таймера. Запомненный вход обменивается только в `boot()`, и `trustedExchangeAttempted` сбрасывается в `beginNewCycle()`. После отказа обмена credential удаляется, а страница молча показывает обычную форму кода. Галочка `remember-browser` по умолчанию выключена, и `clearPairingForm` сбрасывает её в выключенное состояние.

## Goals / Non-Goals

**Goals:**
- Ответчик mDNS без сторонних библиотек. Он отвечает только на одно имя и полностью покрыт тестами JVM без сети.
- Адрес по имени не ослабляет защиту от DNS rebinding: разрешено только занятое имя, а не любое `.local`.
- Любой сбой mDNS оставляет сервер работать по IP, как сейчас.

**Non-Goals:**
- Объявление служб DNS-SD, поиск других телефонов, IPv6.
- Смена имени «на лету» без перезапуска сервера.
- Автоматическая замена старого корня.
- Продление запомненного входа.

## Decisions

### 1. Свой минимальный ответчик mDNS вместо NsdManager или JmDNS

**Выбор:** класс `LocalNameResponder` на `MulticastSocket` (224.0.0.251:5353). Разбор и сборку пакетов делает отдельный `MdnsCodec` без сети.

**Что ответчик делает:**
- отвечает записью A на запросы A и ANY о занятом имени;
- на запрос AAAA отвечает записью NSEC «нет IPv6» (RFC 6762 §6.1), чтобы Windows не ждал тайм-аут;
- проверяет имя перед занятием (probe);
- объявляет имя и отзывает его (goodbye, TTL 0).

**Отвергнуто:**
- `NsdManager`: не даёт задать имя хоста.
- JmDNS: большая и давно почти не обновляемая библиотека. Она объявляет службы, а нам нужна одна запись A, при этом каждый её ответ пришлось бы проверять.

**Устойчивость разборщика:** пакет не больше 9000 байт, указатели сжатия только назад и не больше 16 переходов, ограниченное число записей. Неверный пакет отбрасывается молча.

### 2. Кому и как отвечать

- **Только в своей подсети.** Ответчик принимает запросы только с интерфейса опубликованного endpoint. Запросы с адреса вне подсети этого интерфейса он игнорирует (RFC 6762 §11).
- **Многоадресный ответ.** Он уходит на 224.0.0.251:5353 с TTL 120 и битом cache-flush.
- **Запрос с «чужого» порта (не 5353, legacy unicast).** Ответ идёт одноадресно на порт отправителя, с тем же ID, вопросом и TTL не больше 10.
- **Запрос с битом QU.** Ответ идёт одноадресно отправителю, а если прошло больше секунды с прошлого многоадресного ответа, то и многоадресно.
- **Зачем одноадресные ответы.** Windows с профилем сети «Общедоступная» может не принимать входящие многоадресные ответы mDNS.
- **Ограничение частоты.** Не больше одного многоадресного ответа на запись в секунду.

### 3. Проверка имени и конфликты

**Проверка перед занятием:**
- 3 запроса-пробы с интервалом 250 мс, тип ANY, с нашей записью A в секции authority.
- Если любой ответ содержит запись о проверяемом имени с другими данными, это конфликт.
- Если одновременно чужая проба на то же имя, сравниваем данные по правилу RFC 6762 §8.2. Проигравший считает это конфликтом.
- При конфликте проверяется следующее имя: `имя-2`, …, `имя-9`. Суффиксы до `-9` укладываются в предел длины: 40 + 2 символа.
- После успешной проверки 2 объявления с интервалом 1 с.

**Конфликт во время работы** (чужой ответ с тем же именем и другим адресом):
- Ответчик перестаёт отвечать и сообщает координатору.
- Адрес по имени пропадает до следующего запуска.
- Повторная проверка «на лету» потребовала бы менять сертификат и разрешённые адреса в работающем сервере. Такой конфликт бывает только с устройством, которое не соблюдает RFC.

### 4. Порядок запуска и остановки

**Запуск:**
1. Выбор IP (`LanEndpointResolver`).
2. `MulticastLock` и проверка имени. Добавляет около 0,75 с к запуску.
3. `prepareTls(ip, claimedName)`.
4. Слушатели.
5. Объявление имени.
6. Публикация `ServerEndpoint`.

**Остановка:** отзыв имени (goodbye), освобождение `MulticastLock` и только потом закрытие слушателей. Это происходит при любой причине остановки, включая смену сети.

**Если сокет 5353 не открылся:** `claimedName = null`, у endpoint статус `NameUnavailable`, запуск продолжается по IP.

**Разрешение:** `CHANGE_WIFI_MULTICAST_STATE`. Оно normal и выдаётся без запроса пользователю. `MulticastLock` держится только пока сервер запущен.

### 5. Модель адреса

`ServerEndpoint` получает три новых свойства:
- `localName: String?`: полное имя, например `devicebridge.local`;
- `nameStatus`:
  - `Claimed(requestedTaken: Boolean)`;
  - `Unavailable(reason = TAKEN_ALL | NETWORK | CERTIFICATE)`;
- `ipAuthority` (`ip:port`) для перенаправления.

`url` использует имя, если оно есть. Вход один: пока имя занято, `allowedAuthorities` содержит только `"$localName:$port"`, а первым в конвейере Ktor стоит `installAddressRedirect`. Он отвечает на запрос страницы с `Host` вида `ip:port` перенаправлением 308 на тот же путь по имени (с `https`, если соединение пришло через TLS) и отклоняет API по IP с 403. При потере имени во время работы перенаправление снимается, а `allowedAuthorities` снова содержит только IP. Главный экран и уведомление сервера показывают только `url` и объяснение из `nameStatus`.

Отвергнуто: оставить IP вторым входом. Пользователь хочет один адрес, и закладка по IP иначе продолжала бы работать мимо имени. Цена решения: если сеть не пропускает mDNS, а телефон всё же занял имя, компьютер не откроет страницу. Поэтому в этом случае нужна ручная проверка сети (task 8.3), а имя, которое не удалось занять, по-прежнему оставляет вход по IP.

### 6. Сертификаты: зона `local` и старые корни

**Новые корни** получают permitted dNSName `local`. По RFC 5280 такое ограничение допускает все имена вида `x.local` и не допускает публичные имена. Частные диапазоны IPv4 остаются.

**Старые корни:**
- Они разрешали только `devicebridge.local`, и мы их не трогаем.
- Небольшой разборщик читает из расширения NameConstraints корня список permitted dNSName.
- `LocalCertificateAuthority.permits(name)` решает по этому списку.

**В защищённом режиме:**
- Имя, которое корень не допускает, не занимается совсем: ответчик не запускается, `nameStatus = Unavailable(CERTIFICATE)`.
- Настройки защищённого режима показывают подсказку сбросить сертификат.
- Иначе адрес по имени вёл бы на HTTPS с ошибкой сертификата.

**Сертификат сервера:**
- SAN = IP + занятое имя (прежний безусловный `devicebridge.local` убирается).
- CN = занятое имя или IP.
- `covers(ip, name)` проверяет оба значения.

**Отвергнуто:** автоматически пересоздавать старый корень. Установленный на компьютере сертификат молча перестал бы работать.

### 7. Настройка «Имя в сети»

- **Проверка:** value class `NetworkName` в domain: `^[a-z0-9](?:[a-z0-9-]{0,38}[a-z0-9])?$` после приведения к нижнему регистру.
- **Хранение:** ключ `network_name` в `DataStoreSettingsRepository`. Недопустимое значение при чтении заменяется на `devicebridge`.
- **Где поле:** в карточке «Устройство» под «Имя телефона», с неизменяемым суффиксом `.local`.
- **При работающем сервере** показывается подсказка «Новый адрес заработает после перезапуска сервера». Новое имя просто читается при следующем запуске.

### 8. Действия в уведомлении о запросе подключения

- **Новые действия** `DENY_PAIRING`, `ALLOW_PAIRING` и `ALLOW_AND_REMEMBER_PAIRING` в `EventNotificationAction` идут через тот же приёмник и реестр.
- **Коды запросов.** `ACTION_SLOTS` увеличивается до 16, а `CONTENT_SLOT` становится 15, потому что действий теперь 9.
- **Разблокировка.** Кнопки разрешения строятся с `setAuthenticationRequired(true)`, и добавляются только на API 31+. На API 29-30 остаются «Отклонить» и текст «Откройте DeviceBridge, чтобы разрешить».
- **Что вызывают кнопки.** Обработчик вызывает те же `ApproveBrowserRequestUseCase(ALLOW_ONCE | ALLOW_AND_REMEMBER)` и `DenyBrowserRequestUseCase`, что и `HomeViewModel`. Ошибку «запрос уже не ожидает решения» он проглатывает и убирает уведомление.
- **Отвергнуто:** требовать разблокировку и для «Отклонить». Отклонение безопасно, а лишний шаг мешает.

### 9. Web: ожидание телефона

- **Новое состояние** `waiting{nextCheckInMs}` в `SessionController`. Оно заменяет конечные `needsUserAction(reconnect_exhausted)` и `offline` без таймера. Быстрые попытки (3 переподключения WebSocket и 3 проверки при загрузке) остаются как есть.
- **Опрос.** В ожидании `AvailabilityWaiter` запрашивает `/web-manifest.json`:
  - интервал 3 с, пока вкладка видна, и 15 с, пока скрыта;
  - при `visibilitychange` → visible, `online` и «Проверить сейчас» проверка идёт сразу;
  - одновременно выполняется только один запрос.
- **Успех** запускает `beginNewCycle()` и `boot()`. Старый token получит 401 и будет удалён, затем выполнится обмен запомненного входа, иначе появится форма с пометкой «Телефон снова доступен».
- **Отзыв при работающем сервере** (WebSocket 1008, `sessionLost`) в ожидание не переводит. Так отключённая на телефоне session не восстанавливается сама.
- **Уведомления на компьютере.** `eventNotificationController` считает переход в `waiting` потерей связи так же, как `offline`.

### 10. Web: запомненный вход и галочка

- **Отказ обмена.** При отказе (`UNAUTHORIZED`/`EXPIRED`) credential удаляется, как сейчас, а `ready` получает признак `trustRejected`. `shellView` показывает над формой «Этот телефон не узнал браузер…» с тремя возможными причинами. Сервер по-прежнему не сообщает, существовал ли credential.
- **Галочка.** В `index.html` добавляется `checked`, и `clearPairingForm` возвращает её во включённое состояние. Первый challenge создаётся уже с `rememberBrowserRequested = true`, чтобы при отправке с галочкой не было лишнего запроса.
- **Предупреждение HTTP.** В текст добавляется фраза, что в чужой сети другое устройство может выдать себя за телефон.

## Risks / Trade-offs

- **Роутер, гостевая сеть или прокси на компьютере не дают найти имя.** → Если телефон не смог занять имя, он работает и показывает адрес по IP. Если имя занято, но компьютер его не находит, адрес по IP тоже ведёт на имя, и войти нельзя. Это известное ограничение: инструкция советует добавить `*.local` в исключения прокси, а проверка имени перед перенаправлением остаётся на будущее.
- **Windows не принимает многоадресные ответы, когда сеть помечена «Общедоступной».** → Одноадресные ответы на QU и legacy-запросы. Ручная проверка на Windows 11 с обоими профилями сети.
- **Прошивка телефона не даёт открыть порт 5353 рядом с системным mdnsd.** → `SO_REUSEADDR` до bind. Если не получилось, сервер работает по IP и показывает `Unavailable(NETWORK)`.
- **В режиме HTTP имя подделать проще, чем IP.** Любое устройство в сети может ответить на `devicebridge.local` и получить запомненный вход, который браузер предъявит. Это тот же класс угроз, что уже принят для HTTP, где трафик и так не шифруется. → Фраза в предупреждении HTTP. В защищённом режиме подмену остановит проверка сертификата.
- **Два телефона с одним именем по очереди.** Телефон А выключен, телефон Б с тем же именем по умолчанию занял `devicebridge.local`. Браузер А предъявит свой запомненный вход телефону Б, получит отказ и удалит credential. → Сообщение «Этот телефон не узнал браузер» называет эту причину, а главный экран при конфликте советует задать своё имя. Хранить credential после отказа мы не стали: иначе пришлось бы ослабить требование «не раскрывать, существовал ли credential».
- **Запомненный вход привязан к origin.** После перехода с IP на имя браузер один раз проходит вход с кодом. → Упоминание в руководстве пользователя.
- **Эмулятор не проверяет настоящий Wi-Fi и Windows.** → Кодек, ответчик и проверка имени покрыты тестами JVM с поддельным транспортом и часами. Инструментальный тест на эмуляторе опрашивает ответчик через свой `MulticastSocket` на том же интерфейсе. Разрешение имени в Windows проверяется вручную на телефоне и компьютере пользователя.
- **Бесконечное ожидание вкладки.** Её запросы крошечные (manifest, раз в 3-15 с), и идут они только по локальной сети. Если компьютер ушёл в другую сеть, это просто безуспешный поиск имени.

## Migration Plan

- Имя по умолчанию `devicebridge` появляется само после обновления, настройка не нужна.
- Старый корень продолжает работать для `devicebridge.local` и IP. Для своего имени или суффикса пользователь один раз нажимает «Сбросить сертификат» и устанавливает новый корень.
- Откат: если ответчик выключить, всё работает по IP, как до change. Формат данных меняется только добавлением ключа `network_name`.
