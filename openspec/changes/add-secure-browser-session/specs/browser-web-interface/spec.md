## ADDED Requirements

### Requirement: Web shell выполняет pairing с подтверждением на телефоне

Web shell MUST предоставлять доступную форму шестизначного pairing code и MUST отображать отдельные состояния отправки, ожидания решения на телефоне, подключения, неверного или истёкшего кода, временной блокировки, отказа и отзыва session. До успешного решения Android host страница MUST NOT считать browser client подключённым.

#### Scenario: Пользователь вводит код

- **WHEN** пользователь вводит ровно шесть цифр и отправляет форму
- **THEN** web shell начинает same-origin pairing request и блокирует повторную конфликтующую отправку
- **AND** состояние результата доступно без опоры только на цвет

#### Scenario: Код имеет неверный формат

- **WHEN** поле пусто либо содержит не шесть десятичных цифр
- **THEN** форма показывает локальную понятную ошибку и не отправляет запрос
- **AND** фокус можно вернуть к полю с клавиатуры

#### Scenario: Телефон ожидает подтверждение

- **WHEN** server принял правильный код и создал pending request
- **THEN** web shell показывает состояние «Подтвердите подключение на телефоне»
- **AND** не открывает защищённую домашнюю страницу до ответа Android host

#### Scenario: Pairing разрешён

- **WHEN** server возвращает разрешённую session и token
- **THEN** web shell сохраняет token только для текущей browser tab/session и показывает состояние «Подключено»
- **AND** token не отображается пользователю и не добавляется в URL, local storage или cookie

#### Scenario: Session потеряна или отозвана

- **WHEN** защищённый запрос получает `401` либо авторизованный WebSocket закрыт из-за отзыва session
- **THEN** web shell удаляет локальный token и возвращается к pairing state
- **AND** показывает понятную причину и действие повторного подключения

## MODIFIED Requirements

### Requirement: Страница честно отображает доступность локального web server

Web shell MUST проверять доступность совместимой версии локального web server через публичный same-origin `GET /web-manifest.json`. Manifest MUST считаться web asset, содержать только версии протокола и web assets и MUST NOT содержать токены, идентификаторы устройства или другие секреты. После pairing фактический session status MUST загружаться только через защищённый `GET /api/v1/status`.

#### Scenario: Локальный web server доступен

- **WHEN** `/web-manifest.json` возвращает успешный совместимый ответ без session token
- **THEN** страница показывает, что DeviceBridge доступен для pairing
- **AND** отображает версию протокола и версию web assets без приватного состояния

#### Scenario: Статус недоступен

- **WHEN** запрос manifest завершается сетевой ошибкой, timeout или несовместимым ответом
- **THEN** страница показывает понятное состояние потери соединения
- **AND** предоставляет ограниченный автоматический retry и явное действие повторной проверки

#### Scenario: Неавторизованный API статуса не опубликован

- **WHEN** браузер без действующего session token запрашивает `/api/v1/status`
- **THEN** сервер возвращает `401 Unauthorized` без сведений о состоянии устройства
- **AND** публичная проверка доступности использует только `/web-manifest.json`

#### Scenario: Авторизованный status доступен

- **WHEN** подключённый browser client запрашивает `/api/v1/status` с действующим token
- **THEN** web shell показывает фактическое подключённое состояние текущей session
- **AND** не получает codes или tokens других clients

### Requirement: Недоступные функции не имитируют готовую работу

После появления session authorization web shell MUST позволять выполнить pairing, но MUST NOT позволять отправлять текст, загружать или скачивать файлы до реализации соответствующих changes. Интерфейс MUST различать успешное подключение браузера и готовность transfer capabilities.

#### Scenario: Пользователь открывает web shell третьего этапа

- **WHEN** локальный server доступен, но browser client ещё не авторизован
- **THEN** пользователь видит pairing form и недоступные transfer actions
- **AND** HTTP availability не обозначается как авторизованная WebSocket session

#### Scenario: Browser успешно подключён

- **WHEN** pairing завершён и session token действителен
- **THEN** web shell показывает подключённое состояние и защищённый server status
- **AND** формы текста и файлов остаются недоступными с объяснением следующего этапа
