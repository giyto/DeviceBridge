## Context

Мотивация — в proposal.md. Как работает передача сейчас:

- **Browser → Android.** Offer `POST /api/v1/files` содержит SHA-256 всего файла; браузер считает его заранее, потоково. После approve браузер одним XHR отправляет весь `File` в `POST /api/v1/files/{id}` без offset. `RawFileUploadProcessor` хеширует байты по мере записи. Запись идёт в `<name>.devicebridge-partial`, который `PartialDocumentManager` создаёт и открывает в режиме `"w"`. После совпадения SHA-256 документ переименовывается. При любой ошибке `abort()` удаляет partial.
- **Retry.** `FileTransferCoordinator.retry` удаляет destination и возвращает item в QUEUED с нулём байтов. Поэтому B→A снова требует approve.
- **Потеря WebSocket.** Все незавершённые transfers session получают FAILED(SessionUnavailable).
- **Смена сети или адреса.** Server generation останавливается, `close()` отменяет всё.
- **Android → Browser.** Одноразовый grant живёт 30 с. `GET /api/v1/files/{id}?grant=…` всегда отдаёт `200` без Range и ETag. Браузер скачивает через нативную загрузку `<a download>`.
- **Версия протокола.** `FILE_PROTOCOL_VERSION = 1` объявлена отдельно в Kotlin и в TS. Web shell поставляется в том же APK.

Главное ограничение: самый частый обрыв на телефоне — потеря Wi-Fi или смена адреса — завершает server generation. Если продолжение привязать только к transfer identifier внутри generation, оно не поможет в основном сценарии.

## Goals / Non-Goals

**Goals:**
- Продолжать B→A upload после любого обрыва: внутри той же вкладки, после reconnect, после перезапуска сервера и после обновления страницы.
- Продолжать A→B download штатным «Возобновить» браузера в пределах generation.
- Не ослаблять подтверждение, лимиты и итоговую проверку SHA-256.

**Non-Goals:**
- Автоматическое продолжение без действия пользователя: остаётся принцип manual retry.
- Продолжение A→B после перезапуска сервера: grant и source живут только внутри generation.
- Параллельная отправка частей одного файла и multi-range ответы.
- Продолжение файлов меньше 8 МиБ.

## Decisions

### D1. Продолжение B→A по содержимому, а не по transfer identifier

Незавершённая часть идентифицируется ключом (SHA-256, размер, display name, destination tree). Новый offer с тем же SHA-256, размером и именем, подтверждённый в ту же папку, продолжает существующую часть. Внутри generation «Продолжить» использует тот же механизм для того же transfer identifier.

*Альтернатива:* resume token, привязанный к transferId и session. Отклонена: он не переживает смену сети и остановку сервера, то есть основной сценарий.

Offer уже содержит SHA-256 всего файла, поэтому браузер ничего дополнительно не считает. Сопоставление выполняется после approve, когда известна папка.

### D2. Без новой фазы state machine

Прерванный item остаётся `FAILED` с существующей причиной (network, session unavailable, server stop). `bytesTransferred` при переходе в FAILED сохраняется, и web по нему показывает «Продолжить» с уже переданным объёмом. Retry ставит item в QUEUED с нулевым progress, как и сейчас. После подготовки сохранённой части server поднимает progress до offset событием `Progressed`.

Чтобы «Продолжить» внутри generation не требовал повторного approve, coordinator помечает retry item, у которого сохранена часть. Контроллер автоприёма (`TrustedAutoAcceptController`) подтверждает такой item в папку по умолчанию независимо от trust и настройки автоприёма, если сохранённая часть лежит именно в ней. Во всех остальных случаях работает обычное подтверждение.

Для A→B ranged-запрос браузера в окне продолжения считается явной командой retry и переводит item `FAILED → TRANSFERRING` с progress от offset.

*Альтернатива:* фаза `INTERRUPTED`. Отклонена: она затрагивает reducer, историю, web-парсер, уведомление и Home ради того, что уже выражается failed + retry.

### D3. Протокол upload с offset

- Когда item переходит в TRANSFERRING, браузер вызывает `POST /api/v1/files/{id}/upload-offset` (`file.upload_offset.request`). Server готовит output: находит сохранённую часть, восстанавливает SHA-256 по префиксу или создаёт новый partial. Затем отвечает `file.upload_offset` с `offsetBytes`. Подготовленный output хранится до POST payload.
- Браузер отправляет `file.slice(offset)` с заголовком `X-DeviceBridge-Upload-Offset: <offset>` и `Content-Length = size − offset`.
- Server отклоняет несовпадающий offset кодом `409` с ожидаемым offset, не открывая output.
- Изменение совместимое, поэтому `FILE_PROTOCOL_VERSION` остаётся 1. Upload без заголовка offset считается загрузкой с нуля, так что вкладка, открытая до обновления приложения, продолжает работать.

*Альтернатива:* стандартный `Content-Range` в запросе. Отклонена: его семантика в запросах не стандартизована. Собственный заголовок проще валидировать.

### D4. Запись с позиции в SAF

- Partial открывается в режиме `"rw"`. Через `ParcelFileDescriptor` и `FileChannel` выполняются `truncate(offset)` и `position(offset)`.
- Если provider не даёт seekable descriptor или бросает исключение, partial удаляется и передача начинается с нуля (спека, сценарий «Provider не поддерживает запись с позиции»).
- Вместо `abort()` при network failure, потере session и server stop вызывается `retain()`: stream закрывается, partial остаётся, запись обновляется фактическим размером. При явной отмене, checksum mismatch и файлах меньше 8 МиБ, как и раньше, вызывается `abort()`.

### D5. Восстановление SHA-256 по сохранённому префиксу

- Перед приёмом server читает partial через `ContentResolver` и прогоняет байты через `MessageDigest`.
- Offset равен фактически прочитанной длине, а не значению из записи. Так учитываются неполные flush и внешние изменения.
- Для 1 ГиБ это несколько секунд чтения. Web и Android показывают этап «Проверка сохранённой части» в фазе CONNECTING.

*Альтернатива:* сериализация состояния digest. Отклонена: `MessageDigest` не сериализуется, а чтение префикса заодно проверяет, что он на месте.

### D6. Хранилище записей — таблица Room в существующей БД

- Таблица `partial_uploads` содержит: key (sha256, size, name, treeUri), partialDocumentUri, mime, bytes, updatedAt.
- Эта БД уже исключена из Android backup вместе с историей. Нужна миграция схемы.
- Cleanup удаляет записи старше 24 ч и записи без существующего partial. Он выполняется при старте приложения, при старте сервера и перед сопоставлением offer.

*Альтернатива:* DataStore JSON. Отклонена: нужны поиск по ключу и транзакции.

### D7. Порог 8 МиБ и срок 24 часа

Мелкие файлы быстрее отправить заново, а порог не даёт засорять папку `*.devicebridge-partial`. 24 часа достаточно, чтобы переподключиться и отправить файл повторно, и не оставляют мусор надолго. Оба значения — константы, настройками они не становятся.

### D8. Range для download

- `GET` отвечает с `Accept-Ranges: bytes` и `ETag: "sha256-<hex>"`. Хеш уже считается при подготовке source.
- Поддерживаются одиночные диапазоны `bytes=N-` и `bytes=N-M` с ответом `206` и `Content-Range`. Всё остальное получает `416`.
- `If-Range` с другим ETag или изменённый source дают `412` без содержимого.
- Grant остаётся одноразовым для полного скачивания. Для ranged-продолжения того же item он принимается повторно в течение 15 минут после обрыва, пока item в FAILED(StreamFailed) и generation не сменилась.
- Если в направлении A→B уже идёт другой download, ranged-запрос получает `409`. Web UI подсказывает повторить позже.

### D9. Остановка сервера сохраняет B→A части

`FileTransferCoordinator.close()` для B→A items размером от 8 МиБ вызывает `retain()` вместо `abort()`. Очередь и items при этом отменяются, как и раньше: спека запрещает восстанавливать очередь прошлого generation.

## Risks / Trade-offs

- **[Облачные SAF providers не поддерживают seekable запись]** → fallback на запись с нуля (D4). E2E-проверка выполняется на локальной папке Download.
- **[Partial documents видны в папке пользователя]** → суффикс `.devicebridge-partial`, срок 24 ч, счётчик и удаление в Settings. То же имя используется и сейчас, пока идёт передача.
- **[Чтение префикса 1 ГиБ перед продолжением]** → отдельный этап в UI. Оно всё равно быстрее повторной передачи по Wi-Fi.
- **[Повреждённый префикс обнаруживается только в конце]** → итоговый SHA-256 обязателен. При несовпадении часть удаляется и следующий retry начинается с нуля.
- **[Браузер возобновляет download, пока направление занято]** → `409` и подсказка в UI. Окно в 15 минут даёт время повторить.
- **[Проверка свободного места учитывала весь размер]** → при продолжении требуется место только для оставшихся байтов.

## Migration Plan

1. Room-миграция добавляет таблицу `partial_uploads`. Существующие данные истории не меняются.
2. Новые сообщения протокола выкатываются одновременно в Kotlin и в web assets того же APK. Старые клиенты без offset работают как раньше.
3. Откат на предыдущую версию APK не поддерживается штатно: downgrade Room. Оставшиеся `*.devicebridge-partial` пользователь при необходимости удалит сам. Руководство это упоминает.
