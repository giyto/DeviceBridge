# Техническое задание DeviceBridge

## 1. Общая информация

**Название:** DeviceBridge

**Версия документа:** 2.1

**Целевая версия продукта:** MVP 1.0

**Тип продукта:** одно устанавливаемое Android-приложение со встроенным локальным веб-сервером
**Основной сценарий:** передача текста, ссылок и файлов между Android-телефоном и браузером компьютера в одной локальной сети

DeviceBridge позволяет пользоваться телефоном и компьютером как связанными устройствами без установки отдельной программы на Windows, без аккаунта, облака и внешнего backend. Пользователь запускает сервер внутри Android-приложения, открывает показанный адрес в браузере компьютера и подтверждает подключение одноразовым кодом.

Веб-интерфейс компьютера является частью Android-приложения: его статические файлы собираются вместе с проектом, помещаются в APK и отдаются встроенным сервером. Таким образом, разрабатывается и устанавливается только одно приложение.

## 2. Цель продукта

Создать личный инструмент для ежедневной быстрой передачи данных между собственным Android-телефоном и компьютером без использования мессенджеров, USB-кабеля или облачного диска.

MVP должен решать четыре основные задачи:

1. открыть DeviceBridge на компьютере через браузер;
2. передать текст или ссылку в обе стороны;
3. передать один или несколько файлов в обе стороны;
4. показать пользователю состояние, прогресс и результат каждой операции.

## 3. Границы системы

### 3.1 Компоненты

Система состоит из следующих компонентов:

- Android UI на Jetpack Compose;
- локальный HTTP/WebSocket-сервер внутри Android-приложения;
- встроенный браузерный интерфейс на HTML, CSS и TypeScript;
- локальное хранилище истории и настроек на телефоне;
- системная Android-интеграция «Поделиться»;
- foreground service, поддерживающий сервер во время активной сессии.

### 3.2 Схема работы

```text
+--------------------------------------+
| Android DeviceBridge                 |
|                                      |
| Compose UI                           |
| Domain / Use Cases                   |
| Embedded HTTP + WebSocket server     |
| Room / DataStore / Keystore          |
| Bundled web assets                   |
+------------------+-------------------+
                   |
             Local Wi-Fi LAN
                   |
                   v
+--------------------------------------+
| Browser on a computer                |
| Chrome / Edge                        |
|                                      |
| Text and link exchange               |
| File upload and download             |
| Transfer progress                    |
+--------------------------------------+
```

### 3.3 Условия работы

- телефон и компьютер находятся в одной локальной Wi-Fi сети;
- мобильная точка доступа телефона также может использоваться, если компьютер подключён к ней;
- Android-приложение запущено, а локальный сервер включён пользователем;
- для получения событий на компьютере вкладка DeviceBridge должна оставаться открытой;
- интернет для передачи данных не требуется.

## 4. Пользователи и термины

В MVP предусмотрен один пользователь — владелец телефона и компьютера.

- **Android host** — телефон, на котором запущено приложение и локальный сервер.
- **Browser client** — вкладка браузера компьютера, подключённая к Android host.
- **Session** — авторизованное соединение браузера с приложением.
- **Transfer** — передача текста, ссылки или файла в одном направлении.
- **Trusted browser** — браузер, которому пользователь разрешил повторное подключение без нового одноразового кода в течение заданного срока.

## 5. Пользовательские сценарии

### 5.1 Первый запуск

1. Пользователь запускает Android-приложение.
2. Приложение объясняет, что передача выполняется только внутри локальной сети.
3. Приложение запрашивает необходимые разрешения в момент использования соответствующей функции.
4. Главный экран показывает, что сервер остановлен.
5. Пользователь нажимает «Запустить DeviceBridge».
6. Приложение показывает локальный адрес и одноразовый код подключения.

### 5.2 Подключение компьютера

1. Пользователь открывает на компьютере адрес вида `http://192.168.1.25:53317`.
2. Веб-интерфейс запрашивает одноразовый код.
3. Пользователь вводит код, показанный на телефоне.
4. Android-приложение показывает информацию о попытке подключения.
5. Пользователь подтверждает браузер.
6. Сервер выдаёт браузеру случайный session token.
7. Оба интерфейса показывают состояние «Подключено».

### 5.3 Передача текста или ссылки с телефона

1. Пользователь вводит текст в DeviceBridge либо выбирает «Поделиться → DeviceBridge» в другом приложении.
2. Приложение показывает предпросмотр содержимого.
3. Пользователь подтверждает отправку.
4. В подключённом браузере появляется карточка с текстом или ссылкой.
5. Пользователь копирует текст либо открывает ссылку.

### 5.4 Передача текста или ссылки с компьютера

1. Пользователь вводит текст или ссылку в веб-интерфейсе.
2. Нажимает «Отправить на телефон».
3. Android-приложение показывает полученное содержимое.
4. Пользователь копирует текст или открывает ссылку явным действием.

### 5.5 Передача файла с телефона

1. Пользователь выбирает один или несколько файлов через системный Android picker или меню «Поделиться».
2. До отправки приложение показывает черновик выбранных файлов с именем и размером каждого элемента.
3. Пользователь может удалить отдельный файл только из черновика, очистить черновик или добавить другие файлы; оригиналы в хранилище при этом не удаляются.
4. После явного подтверждения приложение добавляет оставшиеся файлы в очередь.
5. Подключённый браузер получает предложение скачать файлы.
6. Пользователь подтверждает загрузку в браузере.
7. Интерфейсы показывают прогресс и итог операции.

### 5.6 Передача файла с компьютера

1. Пользователь выбирает файлы кнопкой или перетаскивает их в браузерную страницу.
2. До отправки веб-интерфейс показывает черновик выбранных файлов и позволяет удалить отдельный элемент, очистить черновик или добавить другие файлы без удаления оригиналов с компьютера.
3. После явного подтверждения веб-интерфейс отправляет оставшиеся файлы потоково на телефон.
4. Android-приложение сохраняет их в выбранную пользователем папку либо запрашивает место сохранения.
5. После завершения выполняется проверка SHA-256.
6. Пользователь может открыть файл или перейти к его расположению.

## 6. Функциональные требования

### FR-01. Управление локальным сервером

- Сервер запускается только после явного действия пользователя.
- Приложение показывает текущий IP-адрес, порт, состояние и время работы сервера.
- Сервер привязывается к доступному адресу локальной сети и свободному порту.
- Пользователь может остановить сервер из приложения и foreground-уведомления.
- При смене сети сервер безопасно завершает старую сессию и показывает новый адрес после перезапуска.
- Автоматический запуск после перезагрузки телефона в MVP запрещён.

### FR-02. Веб-интерфейс

- Сервер отдаёт браузерную страницу и необходимые статические ресурсы из APK.
- Интерфейс поддерживает актуальные Chrome и Edge на Windows 10 и Windows 11.
- Интерфейс адаптируется к ширине окна от 360 до 1920 пикселей.
- Страница показывает соединение, активные передачи, историю текущей сессии и ошибки.
- После защищённого подключения страница показывает реальное имя Android-устройства из настроек телефона; публичный manifest это имя не раскрывает.
- При потере WebSocket страница выполняет ограниченное повторное подключение и затем предлагает пользователю обновить адрес или перезапустить сервер.
- Веб-интерфейс не загружает код, шрифты, аналитику или другие ресурсы из интернета.

### FR-03. Авторизация браузера

- При запуске сервера создаётся одноразовый числовой код, действующий не более пяти минут.
- После пяти ошибочных попыток ввод временно блокируется.
- Подключение требует дополнительного подтверждения на телефоне.
- После подтверждения сервер выдаёт криптографически случайный bearer token длиной не менее 128 бит.
- Token передаётся в заголовке или защищённом протокольном сообщении, а не в URL.
- По умолчанию token живёт до остановки сервера.
- Опция «Запомнить этот браузер» может выдать отдельный отзывной token с ограниченным сроком действия.
- Пользователь может увидеть и отозвать все доверенные браузеры в настройках Android-приложения.

### FR-04. Передача текста и ссылок

- Поддерживается UTF-8 текст размером до 100 КБ.
- Направления: Android → Browser и Browser → Android.
- URL распознаётся как ссылка только после безопасного разбора схемы; автоматически открывать полученную ссылку запрещено.
- Для каждого сообщения отображаются отправитель, время, направление и статус.
- Повторная отправка не должна создавать дубликат после уже полученного подтверждения.
- Android-приложение принимает `ACTION_SEND` для `text/plain`.
- Скрытое чтение Android clipboard запрещено; вставка выполняется только при открытом приложении и явном действии пользователя.
- Браузер использует Clipboard API только при наличии разрешённого secure context; иначе показывает выделяемое поле и инструкцию для ручного копирования.

### FR-05. Передача файлов

- Поддерживается выбор одного или нескольких файлов.
- Направления: Android → Browser и Browser → Android.
- До подтверждения отправки выбранные файлы образуют редактируемый черновик, а не очередь передачи.
- На Android и в браузере пользователь может удалить отдельный элемент из черновика, очистить весь черновик и добавить другие файлы.
- Удаление из черновика не удаляет и не изменяет исходный файл в хранилище телефона или компьютера.
- Отмена повторного системного выбора файлов не очищает уже подготовленный черновик.
- Если черновик пуст, действие отправки недоступно; после подтверждения элементы переходят в очередь и управляются действиями отмены и повтора.
- Файлы передаются потоково без чтения всего содержимого в оперативную память.
- MVP должен поддерживать файл размером не менее 500 МБ.
- Для операции показываются имя, размер, переданные байты, проценты, скорость и статус.
- Пользователь может отменить активную операцию.
- Частичный файл после отмены или ошибки не считается завершённым и удаляется либо явно помечается как незавершённый.
- После передачи отправитель и получатель сравнивают SHA-256.
- Совпадение имени не должно приводить к незаметной перезаписи существующего файла.
- Android получает доступ к выбранным файлам и папкам через Storage Access Framework без широкого разрешения на всё хранилище.

### FR-06. Очередь и статусы

- Одновременно выполняется не более одной передачи файла в каждом направлении.
- Остальные операции отображаются в очереди.
- Статусы: `queued`, `connecting`, `transferring`, `verifying`, `completed`, `cancelled`, `failed`.
- Текстовые сообщения могут передаваться во время файловой операции.
- Повтор после сетевой ошибки запускается только пользователем в MVP.

### FR-07. История

- История хранится только на Android-устройстве.
- Для файла сохраняются имя, MIME type, размер, направление, время, checksum и итоговый статус.
- Для текста сохраняются метаданные и безопасный короткий предпросмотр; полный текст может не сохраняться.
- Историю можно очистить полностью или удалить отдельную запись.
- Удаление записи истории не удаляет переданный пользовательский файл.
- Период хранения по умолчанию — 30 дней, значение изменяется в настройках.

### FR-08. Foreground service

- Во время работы сервера Android показывает постоянное уведомление.
- Сервер работает в foreground service типа `connectedDevice`, так как активная сессия является взаимодействием с внешним устройством по локальной сети.
- Уведомление показывает количество подключённых браузеров и активную передачу.
- В уведомлении присутствует действие «Остановить».
- При остановке service все сессии закрываются, незавершённые операции корректно отменяются.
- Длительный Wi-Fi lock допускается только во время активной передачи и освобождается сразу после неё.
- Тип `dataSync` не используется для постоянного ожидания подключения; его применение допускается только как отдельное решение для ограниченной по времени фоновой операции после проверки поведения на поддерживаемых API.

### FR-09. Обработка ошибок

Пользователь должен получать отдельные понятные сообщения для следующих ситуаций:

- телефон и компьютер находятся в разных сетях;
- разрешение локальной сети отклонено или отозвано;
- IP-адрес изменился;
- код истёк или введён неверно;
- браузер не подтверждён на телефоне;
- недостаточно места на телефоне;
- выбранная папка стала недоступна;
- соединение оборвалось;
- checksum не совпал;
- файл превышает установленный лимит;
- формат протокола не поддерживается.

### FR-10. Идентичность приложения

- Android-приложение использует собственную узнаваемую иконку DeviceBridge вместо стандартной иконки шаблона Android Studio.
- Иконка поставляется внутри APK и имеет adaptive foreground/background, legacy fallback для API 29 и monochrome-вариант для системных тематических иконок, где они поддерживаются.
- Иконка сохраняет узнаваемость при системных масках лаунчера и не зависит от внешних ресурсов или сети.
- Название приложения рядом с иконкой отображается как `DeviceBridge`.
- При первом запуске имя устройства формируется из производителя и модели Android-устройства. Точное устаревшее стандартное значение `DeviceBridge Android` заменяется физическим именем; любое другое сохранённое пользователем допустимое имя имеет приоритет и не перезаписывается при обновлении приложения.

### FR-11. Единая визуальная система

- Android UI и встроенный web UI используют единую систему DeviceBridge: тёмную палитру `Midnight Bridge`, светлую `Porcelain Bridge`, строгую информационную структуру `Graphite Professional` и ограниченный статусный feedback `Signal Flow`; platform conventions Android и browser сохраняются.
- Визуальная система определяет semantic design tokens для цвета, типографики, spacing по сетке 4/8, радиусов, границ, elevation и состояний default, hover, pressed, focused, disabled, loading, empty, error, cancelled и success.
- `Midnight Bridge` использует спокойную near-black/graphite основу и слоистые surfaces, `Porcelain Bridge` — нейтральный светлый canvas и белые surfaces; контент не полагается на чистый чёрный/белый контраст или цвет как единственный статус.
- Primary action визуально доминирует, secondary и destructive actions различимы, но не конкурируют с ним; touch/click targets остаются удобными для соответствующей платформы.
- Motion используется только для объяснения переходов состояния и активности соединения/передачи; `prefers-reduced-motion` и отключённые системные анимации заменяют его статичным индикатором без потери смысла.
- Android выбирает Midnight/Porcelain только из системной светлой/тёмной темы. Web предлагает только явные режимы `Светлая` и `Тёмная` в виде одной кнопки-иконки справа от заголовка; выбор сохраняется локально в профиле браузера, не отправляет сетевые команды, а прежнее значение `Системная` безопасно переводится в `Тёмная`.
- UI не использует внешние шрифты, изображения, CDN или runtime-зависимости только ради оформления.

## 7. Экраны Android-приложения

### 7.1 Онбординг

- краткое объяснение принципа работы;
- требование одной локальной сети;
- предупреждение о доверенной сети для MVP;
- переход к запуску сервера.
- короткие последовательные шаги без перегруженных карточек;
- один заметный primary action и возможность повторно открыть инструкции из главного экрана.

### 7.2 Главный экран

- карточка состояния сервера;
- локальный адрес с кнопкой копирования;
- одноразовый код и время его действия;
- кнопки запуска и остановки;
- подключённые браузеры;
- быстрые действия «Текст» и «Файлы»;
- активные передачи.
- крупный status surface как верхний визуальный приоритет;
- отдельный компактный блок адреса и pairing code с понятными copy actions;
- инструкции подключения сворачиваются после успешной browser session и остаются доступными по явному действию;
- bottom navigation на phone и navigation rail на large screen без дублирования разделов и primary actions.

### 7.3 Отправка текста

- поле ввода;
- явная кнопка вставки;
- распознанный тип «Текст» или «Ссылка»;
- предпросмотр;
- подтверждение отправки.
- лента текущей session с визуально различимыми направлениями, отправителем, временем и статусом;
- link actions «Копировать» и «Открыть» остаются внутри карточки и не перекрывают содержимое;
- composer располагается в предсказуемой доступной области и сохраняет введённый draft при recoverable ошибке.

### 7.4 Передача файлов

- системный picker;
- редактируемый черновик выбранных файлов;
- удаление отдельного элемента, очистка списка и добавление других файлов до отправки;
- очередь;
- карточки прогресса;
- отмена и повтор;
- переход к полученному файлу.
- каждая file card показывает type icon, имя, размер, направление, текущий этап и текстовый terminal status;
- progress bar, скорость и оценка оставшегося времени показываются только при наличии достоверных данных и не заменяют текстовый статус;
- действия «Отменить», «Повторить», «Открыть» и «Сохранить» появляются только в применимом состоянии и не выходят за границы карточки.

### 7.5 История

- список операций строится одной широкой скруглённой карточкой на строку без квадратной сетки;
- карточка показывает status, тип, имя файла или безопасный preview, размер файла, направление, browser label и время;
- одна компактная кнопка фильтров показывает количество активных условий и открывает modal bottom sheet;
- в панели фильтров направления, типы и статусы расположены отдельными вертикальными группами, поддерживают выбранное состояние, немедленное применение и общий сброс;
- просмотр деталей, удаление отдельной записи и очистка истории;
- пустое состояние без тестовых записей с коротким объяснением и одним полезным действием, если оно применимо;
- список сохраняет спокойную визуальную плотность без перегруженных вложенных карточек;
- на экранах текста и настроек непотреблённый тап по свободной области снимает focus и закрывает клавиатуру, не очищая draft и не перехватывая кнопки, навигацию или scroll.

### 7.6 Настройки

- имя телефона;
- папка сохранения;
- время хранения истории;
- список доверенных браузеров;
- отзыв token;
- лимит размера файла;
- информация о версии приложения и протокола.
- настройки сгруппированы в логические секции с явными labels и локальной validation рядом с проблемным полем;
- failed save сохраняет draft и визуально отличается от успешно применённого значения.

## 8. Веб-интерфейс компьютера

Веб-интерфейс должен содержать:

- экран ввода одноразового кода;
- состояние ожидания подтверждения на телефоне;
- домашнюю страницу соединения;
- поле отправки текста;
- область drag-and-drop для файлов;
- редактируемый список выбранных, но ещё не отправленных файлов;
- список входящих элементов;
- прогресс активных передач;
- понятное состояние потери соединения;
- компактную кнопку-иконку темы справа от заголовка: солнце обозначает активную светлую тему, луна — активную тёмную; нажатие переключает только `Светлая` / `Тёмная`, а выбранный режим сохраняется локально в профиле браузера;
- общий с Android визуальный язык, status colors и компоненты состояний;
- двухколоночную desktop-компоновку «соединение/устройство» и «текст/файлы/активность» при достаточной ширине;
- одноколоночную компоновку без горизонтальной прокрутки на узком viewport;
- ленту text/link items и file cards с теми же понятиями направления, progress, terminal status и действий, что в Android;
- видимые hover, pressed, focused, disabled и loading states;
- устойчивый layout при длинных адресах, именах файлов, сообщениях, zoom 200% и ширине viewport 360–1920 пикселей.

В MVP веб-интерфейс не устанавливается как PWA и не регистрирует service worker. Это исключает неожиданный фоновый lifecycle и упрощает контроль версии: браузер всегда получает страницу из запущенного APK.

Изменения оформления, темы и presentation-состояния предупреждения не добавляют backend endpoints, не меняют protocol version и не расширяют возможности pairing, текста, файлов или удалённого доступа.

## 9. Архитектура

### 9.1 Общий подход

Используется прагматичная Clean Architecture, MVVM для Android UI, однонаправленный поток данных и SOLID для компонентов с реальными границами ответственности.

```text
Compose UI
    |
    v
ViewModel + UiState + UiAction
    |
    v
Use Cases
    |
    v
Domain interfaces
    ^
    |
Repositories / Embedded server / Storage / Android APIs
```

Зависимости направлены к domain-слою. ViewModel не должен работать напрямую с Ktor, Room, `ContentResolver`, foreground service или Android Keystore.

### 9.2 Модули и пакеты

До появления измеримой проблемы сборки Android остаётся одним Gradle-модулем `app`. Внутри используются пакеты:

```text
ru.hznik.devicebridge
+-- app
+-- domain
|   +-- model
|   +-- repository
|   +-- usecase
+-- data
|   +-- local
|   +-- server
|   +-- repository
+-- feature
|   +-- home
|   +-- session
|   +-- text
|   +-- transfer
|   +-- history
|   +-- settings
+-- core
    +-- protocol
    +-- security
    +-- ui
```

Веб-исходники располагаются отдельно:

```text
web/
+-- src/
+-- tests/
+-- package.json

app/src/main/assets/web/   # только результат сборки, создаваемый автоматически
```

### 9.3 Применение SOLID

- сервер, история, безопасность и UI имеют отдельные ответственности;
- domain зависит от небольших repository-интерфейсов;
- сетевые и локальные реализации заменяются fake-реализациями в тестах;
- новые типы transfer добавляются через расширение протокола без изменения существующих сценариев;
- интерфейсы создаются только на настоящих границах, а не для каждого класса.

## 11. Локальный протокол

### 11.1 Версионирование

- Все endpoint располагаются под `/api/v1`.
- Каждое WebSocket-сообщение содержит `protocolVersion`, `messageId`, `type` и `timestamp`.
- Неизвестная major-версия отклоняется с понятной ошибкой.
- Повтор `messageId` не должен повторно выполнять уже подтверждённое действие.

### 11.2 Минимальный API

```text
GET    /                         web interface
GET    /assets/*                 bundled static assets
POST   /api/v1/session/challenge begin authorization
POST   /api/v1/session/confirm   confirm one-time code
DELETE /api/v1/session           close current session
GET    /api/v1/status            server and connection status
POST   /api/v1/text              send text to Android
POST   /api/v1/files             upload file to Android
GET    /api/v1/files/{id}        download file from Android
DELETE /api/v1/transfers/{id}    cancel transfer
WS     /api/v1/events            events, acknowledgements and progress
```

Конкретные payload и коды ошибок фиксируются отдельной OpenSpec capability до реализации transfer-функций.

## 12. Безопасность и модель угроз

### 12.1 Защищаемые данные

- содержимое текста и файлов;
- session token и trusted-browser token;
- история операций;
- выбранные пользователем URI;
- технические журналы.

### 12.2 Обязательные меры MVP

- сервер доступен только во время явно запущенной сессии;
- все API, кроме web assets и начала авторизации, требуют token;
- одноразовый код имеет короткий срок и ограничение попыток;
- новое подключение подтверждается на телефоне;
- CORS запрещает сторонние origins;
- проверяются `Origin`, `Host`, MIME type, размер и имена файлов;
- web UI не вставляет полученный текст как HTML;
- журналы не содержат содержимое transfer, коды и tokens;
- tokens генерируются криптографически безопасным генератором;
- trusted tokens хранятся на Android в зашифрованном виде и могут быть отозваны;
- сервер прекращает работу при потере локальной сети или отзыве разрешения.

### 12.3 Ограничение транспортной защиты MVP

Локальный адрес с динамическим IP не позволяет получить обычный публично доверенный TLS-сертификат без дополнительного сервиса, домена или установки локального сертификата на компьютер. Поэтому базовый MVP использует HTTP/WebSocket только в доверенной домашней сети и явно предупреждает пользователя не передавать чувствительные данные через публичный или чужой Wi-Fi.

Session token защищает от случайного и неавторизованного использования API, но не шифрует трафик от участника той же сети. Это осознанное ограничение одно-приложной архитектуры, а не заявленная полная защита.

Web UI показывает предупреждение о доверенной сети как единую раскрываемую поверхность: нажатие на карточку сворачивает пояснение до компактной строки, повторное нажатие раскрывает его. Состояние хранится только как browser-local presentation preference и не изменяет HTTP/WebSocket transport, pairing, session/trusted tokens, CORS, проверку запросов или доступность API.

Для MVP 1.0 выполнен security spike и выбран вариант №4: одно Android-приложение,
локальный HTTP/WebSocket только в доверенной сети и без заявления о шифровании
транспорта. Решение и отклонённые альтернативы зафиксированы в
`docs/decisions/0001-lan-only-mvp.md`. Остальные варианты могут быть реализованы
только отдельным будущим change:

1. локальный HTTPS с управляемым пользовательским доверием к сертификату;
2. защищённый канал на базе WebRTC/DTLS с проверяемым pairing;
3. небольшой desktop companion для полноценной взаимной аутентификации;
4. сохранение LAN-only режима с явной маркировкой как ограниченной локальной утилиты.

## 13. Android-разрешения

Планируемые разрешения:

- `INTERNET` — работа TCP/HTTP/WebSocket;
- `ACCESS_NETWORK_STATE` и `ACCESS_WIFI_STATE` — определение доступности и параметров сети;
- `ACCESS_LOCAL_NETWORK` — входящий и исходящий LAN-трафик при `targetSdk 37`;
- `FOREGROUND_SERVICE`;
- `FOREGROUND_SERVICE_CONNECTED_DEVICE` — работа сервера во время активной локальной сессии;
- `CHANGE_NETWORK_STATE` — manifest prerequisite для foreground service типа `connectedDevice`; приложение не должно самовольно переключать сеть пользователя;
- `POST_NOTIFICATIONS` запрашивается с объяснением, когда это требуется версией Android и выбранным UX.

Широкие разрешения `MANAGE_EXTERNAL_STORAGE` и `READ_EXTERNAL_STORAGE` не используются. Доступ предоставляется пользователем через системный picker.

## 14. Нефункциональные требования

### NFR-01. Производительность

- главный Android-экран становится интерактивным не позднее трёх секунд на тестовом устройстве;
- открытие встроенной страницы в домашней сети занимает не более пяти секунд после установления TCP-соединения;
- файл 500 МБ передаётся потоково без роста памяти пропорционально размеру файла;
- UI остаётся отзывчивым во время checksum и передачи;
- checksum выполняется на фоновом dispatcher.

### NFR-02. Надёжность

- завершённый файл никогда не выдаётся за успешный до проверки checksum;
- потеря браузера не приводит к падению Android service;
- повторный запрос с тем же `messageId` идемпотентен;
- остановка приложения освобождает socket, Wi-Fi lock, файловые дескрипторы и coroutine scopes;
- повреждённая запись истории не блокирует запуск приложения.

### NFR-03. Приватность

- приложение не содержит аналитики и рекламы;
- не выполняются запросы к внешним серверам;
- история и настройки остаются на телефоне;
- пользователь может удалить историю и доверенные браузеры;
- секреты не попадают в Android backup.

### NFR-04. UX и доступность

- Android UI поддерживает Midnight/Porcelain и следует светлой/тёмной теме системы без ручного переключателя приложения;
- web UI поддерживает только локально сохраняемые режимы `Светлая` и `Тёмная`; тема не зависит от `prefers-color-scheme`, а legacy-значение `Системная` мигрирует в `Тёмная`;
- предупреждение доверенной сети сворачивается и раскрывается нажатием на всю карточку; его presentation-состояние не влияет на авторизацию и передачу данных;
- интерактивные элементы имеют доступные названия;
- интерфейс выдерживает системный масштаб шрифта без обрезания основных действий;
- состояния loading, empty, disabled, error, success и cancellation представлены явно;
- пользовательские сообщения формулируются без сетевого жаргона, а технические детали доступны отдельно.
- Android и web используют согласованные design tokens и reusable state surfaces вместо локальных несогласованных стилей;
- primary и secondary actions сохраняют понятную визуальную иерархию, а destructive action не активируется случайно;
- phone использует bottom navigation, large-screen Android — navigation rail, wide web — двухколоночный layout, narrow web — одну колонку;
- TalkBack/screen reader получает значимые stage и terminal transitions, но не каждое изменение progress;
- keyboard focus не теряется после retry, cancellation, закрытия dialog/details или изменения списка;
- reduced-motion preference отключает необязательную motion, не скрывая изменение состояния.

### NFR-05. Совместимость

- Android 10/API 29 — минимальная версия;
- Android 17.1/API 37.1 — основной тестовый образ;
- Chrome и Edge актуальных стабильных версий;
- Windows 10 и Windows 11 как основные desktop-среды браузера;
- IPv4 обязателен для MVP, IPv6 рассматривается после MVP.

## 16. Критерии готовности MVP 1.0

MVP считается готовым, когда одновременно выполнены все условия:

1. Пользователь устанавливает только Android APK.
2. Сервер запускается и останавливается из приложения и уведомления.
3. Компьютер открывает web UI по показанному локальному адресу.
4. Браузер подключается только после кода и подтверждения на телефоне.
5. Текст и ссылки передаются в обе стороны.
6. Один и несколько файлов передаются в обе стороны.
7. Файл 500 МБ проходит передачу и SHA-256 проверку.
8. Отмена и сетевой обрыв не создают файл, ошибочно отмеченный как завершённый.
9. Android Share Target принимает текст и файлы.
10. История корректно отображает успешные, отменённые и неуспешные операции.
11. Отзыв trusted browser немедленно прекращает его доступ.
12. Работа проверена на API 29 и API 37.1.
13. Web UI проверен в Chrome и Edge на Windows 10/11.
14. Приложение не обращается к внешним backend и analytics endpoints.
15. Пользователь видит предупреждение об ограничении HTTP и доверенной локальной сети.
16. Unit-, UI-, web- и интеграционные тесты проходят в заявленной матрице.

## 17. Что не входит в MVP

- отдельное Windows-приложение;
- работа через интернет;
- облачный relay и аккаунты;
- Bluetooth и USB transport;
- screen mirroring и удалённое управление;
- звонки, SMS и полный поток уведомлений;
- автоматическое скрытое чтение clipboard;
- автоматический запуск после загрузки Android;
- фоновая работа без foreground-уведомления;
- PWA и service worker;
- Safari и Firefox как обязательные браузеры;
- IPv6-only сети;
- незаметная перезапись существующих файлов.

## 20. Решение, зафиксированное версией 2.0

DeviceBridge создаётся как **одно Android-приложение**. Компьютер не получает отдельный companion: его роль выполняет браузер, подключённый к серверу телефона. Если ограничения браузера или транспортной безопасности сделают MVP непригодным для ежедневного использования, добавление desktop companion рассматривается только как отдельное будущее изменение, а не скрытая часть текущего объёма.
